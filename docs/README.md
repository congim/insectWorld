# 文档总入口

本目录采用“产品决策 → 架构约束 → 领域设计 → 游戏内容 → 实施证据”的单向文档体系。出现冲突时，按下面的优先级判断，不再以文件日期或篇幅决定权威性。

## 权威层级

| 优先级 | 文档 | 回答的问题 |
|---|---|---|
| 1 | [产品与平台边界](product/产品与平台边界.md) | 我们到底做什么、不做什么 |
| 2 | [目标架构](architecture/目标架构.md) 与已接受 ADR | 系统必须怎样组织、为什么这样决策 |
| 3 | `engine/`、`game/` 下的领域文档 | 某项机制或内容如何工作 |
| 4 | [实施路线图](roadmap/实施路线图.md) | 当前先做什么、如何验收 |
| 5 | `.codeartsdoer/specs/`、日期报告 | 某次任务如何执行、当时验证了什么 |
| 6 | 代码与自动化测试 | 已实现行为的最终事实 |

说明：代码能证明“现在是什么”，产品与 ADR 决定“应该成为什么”。代码与设计不一致时必须显式记录差距，不能悄悄修改文档来迁就偶然实现。

## 文档状态

每份新设计文档应在标题后声明状态：

- `提案`：可讨论，不可直接作为实现依据；
- `已接受`：可以进入实现；
- `已实现`：有代码和测试证据；
- `历史`：仅保留决策背景，不再约束新实现；
- `废弃`：由替代文档接管，不应继续引用。

没有状态的旧文档一律视为“参考资料”，不能覆盖产品边界、目标架构或 ADR。

## 维护规则

- 一个概念只保留一个权威定义，其他文档使用相对链接引用。
- 产品数值、题材名、种族和剧情不得写入通用引擎契约。
- 服务数量、配置文件数量、覆盖率等易变化事实不得散落硬编码；集中写在当前代码地图或可执行配置中。
- 设计稿不写“已完成”；只有测试、构建或运行证据才能声明已实现。
- 日期报告只记录当时结论，不承担持续更新职责。
- 删除被完全替代的草案；有决策价值的旧材料标记为“历史”，不与现行文档并列。
