# 部署策略

> 无状态服务滚动更新，有状态分片逐个更新，配置变更金丝雀，全量发布蓝绿。核心原则：不中断玩家、可快速回滚。

---

## 部署分类

| 服务类型 | 部署策略 | 回滚 | 停机 |
|---------|---------|------|------|
| 无状态（Gateway/Config/Persist） | 滚动更新 | 切旧版 | 0 |
| 有状态分片（World/Combat/Economy/Social） | 分片逐个滚动 | 切旧版 | 0（逐片更新，始终有可用片） |
| 有状态单例主备（Operation） | 先备后主 | 切备 | <5s（主切换瞬间） |
| 配置热更 | 金丝雀→全量 | 切旧配置 | 0 |
| 大版本升级（Schema变更） | 蓝绿 | 切旧环境 | 0（DNS切换） |

---

## 无状态服务滚动更新

```
v1: [实例1] [实例2] [实例3]
         ↓ 滚动
v2: [实例1] [实例2] [实例3]（逐个替换）
    
步骤：
  1. 从LB摘除实例1 → 流量到实例2/3
  2. 实例1优雅停机（完成在途请求，见高可用设计.md）
  3. 部署v2实例1 → 健康检查通过 → 加回LB
  4. 重复实例2、实例3
```

**滚动参数**：maxUnavailable=0（始终保持可用数）、maxSurge=1（多起一个再删旧的）。健康检查通过才加回LB，失败则暂停滚动告警。

## 有状态分片逐个更新

有状态服务不能全量滚动（内存状态会丢），按分片逐个更新，始终保留其他分片服务：

```
World Service 4分片更新：
  分片1: 摘除→停机→部署v2→加回（其他3片持续服务）
  分片2: 摘除→停机→部署v2→加回
  分片3: 摘除→停机→部署v2→加回
  分片4: 摘除→停机→部署v2→加回
```

**关键点**：
- 更新某分片前，确认该分片的备节点已同步最新状态（OpLog追平）。
- 摘除分片期间，该分片流量由备节点接管（<3s切换）。
- 部署v2后，从持久化（Redis/DB）恢复内存状态，健康检查通过才加回。
- 逐片更新间隔>30秒，观察新版本无异常再更新下一片（渐进式确认）。

**Combat Service特殊**：Combat有进行中的战斗。更新某Combat实例前，将其上战斗迁移到其他实例（同故障迁移流程），清空后再停机更新。保证不中断进行中战斗。

## Operation Service主备更新

全局单例主备，先备后主：

```
步骤：
  1. 备节点：停机→部署v2→启动（此时备是v2，主仍是v1）
  2. 主节点：主动切主（etcd选主触发），备(v2)提升为新主
  3. 旧主(v1)：降为备→停机→部署v2→启动为新备
  4. 完成：主=v2, 备=v2
```

**切主瞬间**：赛季操作<5s延迟（选主+状态恢复），可接受。切主时机选在赛季阶段切换间隙（无关键操作时），进一步降低影响。

## 配置热更（金丝雀）

配置变更不重启服务，通过etcd watch热更。但配置错误可能导致业务异常，用金丝雀渐进推广：

```
步骤：
  1. 在etcd写入新配置（version=N+1）
  2. 金丝雀：仅对1个分片/1个实例的共享内核config触发reload
  3. 观察5分钟：业务指标正常？错误率正常？玩家无异常反馈？
  4. 正常→推广到所有实例（etcd watch自动触发各服务reload）
     异常→回滚配置（etcd写回version=N），金丝雀实例自动reload回旧配置
```

**配置版本号**：每份配置带version，业务层记录当前用的version，热更时对比version决定是否切换。防止重复热更或回滚不一致。

## 蓝绿部署（大版本升级）

涉及数据库Schema变更或不可向后兼容的升级，用蓝绿：

```
蓝环境（当前生产）        绿环境（新版）
  v1 + DB schema v1        v2 + DB schema v2
  
步骤：
  1. 部署绿环境（v2），但不接流量
  2. 数据迁移：蓝DB → 绿DB（Schema转换，双写过渡保证不丢）
  3. 验证绿环境数据完整、功能正确
  4. 切流量：DNS/LB从蓝切到绿（瞬间切换）
  5. 观察期：绿环境稳定运行，蓝环境保留作回滚
  6. 确认无误后下线蓝环境
```

**数据迁移**：蓝绿期间双写（写蓝同时写绿），保证迁移中数据不丢。Schema迁移由Persist Service执行（见README.md的Persist职责）。

**回滚**：发现问题→DNS切回蓝环境（<1分钟）。绿环境数据可能比蓝新（切流量后写过绿），回滚时需取舍这部分数据（通常可丢，或事后补）。

---

## 回滚策略

| 场景 | 回滚方式 | 耗时 |
|------|---------|------|
| 无状态服务版本问题 | 滚动回退到旧版镜像 | <2分钟 |
| 有状态分片版本问题 | 逐片回退旧版（从持久化恢复状态） | <5分钟 |
| 配置热更问题 | etcd写回旧配置version，自动reload | <10秒 |
| 蓝绿升级问题 | DNS切回蓝环境 | <1分钟 |
| 数据库Schema问题 | 蓝绿回滚（蓝环境Schema未变） | <1分钟 |

**回滚前提**：每次部署保留旧版本镜像+旧配置版本，至少保留2个版本。数据库迁移必须可逆（提供down迁移脚本），或用蓝绿避免直接改生产Schema。

## 发布门禁

| 门禁 | 检查 | 不过则 |
|------|------|--------|
| 测试全过 | 单元+集成+契约 | 阻止部署 |
| 镜像扫描 | 无高危漏洞 | 阻止部署 |
| 配置校验 | 新配置通过validator | 阻止热更 |
| 健康检查 | 新实例健康通过才加回LB | 暂停滚动 |
| 灰度指标 | 金丝雀期间错误率/延迟不退化 | 自动回滚 |

---

## 维护窗口

| 操作 | 窗口 | 说明 |
|------|------|------|
| 常规滚动更新 | 任意时间 | 无停机，玩家无感 |
| 蓝绿大版本 | 低峰期（凌晨3-5点） | 切流量瞬间有<1s重连，选低峰 |
| Schema迁移 | 维护公告窗口 | 提前公告，双写过渡降风险 |
| 赛季重置 | 赛季结束时刻 | 赛季重置本就要停服片刻，合并部署 |
