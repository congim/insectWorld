# 服务通信

> 微服务间通过gRPC同步调用 + NATS异步事件通信。领域事件驱动服务间数据同步，避免分布式事务。

---

## 通信方式分类

| 通信方式 | 使用场景 | 协议 | 特点 |
|---------|---------|------|------|
| gRPC同步调用 | 需要即时响应的查询 | gRPC/Protobuf | 低延迟、强类型、阻塞 |
| NATS异步事件 | 领域事件传播、状态同步 | NATS/Protobuf | 解耦、可靠、最终一致 |
| etcd watch | 配置变更通知 | etcd | 推送式、强一致 |
| WebSocket推送 | 服务端→客户端推送 | WebSocket/Protobuf | 长连接、实时 |

### 何时用同步 vs 异步

| 场景 | 选择 | 原因 |
|------|------|------|
| Combat查询玩家属性 | gRPC同步 | 战斗开始前需要立即获取参战方属性 |
| 战斗结束通知经济系统 | NATS异步 | 战利品发放不需要即时完成 |
| 移动到达通知战斗系统 | NATS异步 | 是否触发战斗由战斗系统自行判断 |
| 赛季阶段切换通知所有服务 | NATS异步 | 广播通知，不需要响应 |
| 玩家上线查询完整状态 | gRPC同步 | 需要聚合多个服务数据返回客户端 |
| 资源变更通知赛季积分 | NATS异步 | 积分更新不需要即时 |

## gRPC服务定义

### 服务间gRPC接口

```protobuf
// ===== World Service =====
service WorldService {
  rpc GetEntityPosition(GetPositionRequest) returns (PositionResponse);
  rpc GetMapSnapshot(MapSnapshotRequest) returns (MapSnapshotResponse);
  rpc CheckPassable(CheckPassableRequest) returns (CheckPassableResponse);
}

// ===== Combat Service =====
service CombatService {
  rpc GetEntityAttributes(GetAttributesRequest) returns (AttributesResponse);
  rpc GetCombatState(GetCombatStateRequest) returns (CombatStateResponse);
}

// ===== Economy Service =====
service EconomyService {
  rpc GetPlayerResources(GetResourcesRequest) returns (ResourcesResponse);
  rpc CheckSufficient(CheckSufficientRequest) returns (CheckSufficientResponse);
}

// ===== Social Service =====
service SocialService {
  rpc GetPlayerInfo(GetPlayerInfoRequest) returns (PlayerInfoResponse);
  rpc GetDiplomacyStatus(GetDiplomacyRequest) returns (DiplomacyResponse);
  rpc CheckAlliancePermission(CheckPermissionRequest) returns (PermissionResponse);
}

// ===== Operation Service =====
service OperationService {
  rpc GetCurrentSeason(GetSeasonRequest) returns (SeasonResponse);
  rpc GetRanking(GetRankingRequest) returns (RankingResponse);
}
```

### gRPC调用约束

| 约束 | 说明 |
|------|------|
| 超时 | 每次gRPC调用超时2秒，超时返回错误 |
| 重试 | 查询类调用可重试3次；写操作可重试3次，依赖请求ID幂等去重（服务端记录已处理请求ID，重复请求返回首次结果，不重复变更） |
| 请求ID | 每个请求携带全局唯一request_id（UUID），服务端用request_id做幂等键，TTL=5分钟 |
| 熔断 | 错误率>50%触发熔断，30秒后半开试探 |
| 限流 | 每服务对每调用方限流1000 QPS |

**为什么写操作也允许重试**：网络超时时调用方无法确定服务端是否已处理（可能已处理但响应丢失）。若禁止重试则丢请求；允许重试+请求ID幂等，则重复请求被服务端识别并返回首次结果，既不丢请求也不重复变更。这是比"禁止重试"更鲁棒的策略。

|---------|--------|--------|------|

| world.movement.arrived | World | Combat, Gateway | 移动到达，可能触发战斗 |
| world.movement.cross_region | World | World(其他分片) | 跨区域移动交接 |

| combat.ended | Combat | Economy, Operation, Gateway | 战斗结束，触发战利品和积分 |
| combat.report.generated | Combat | Persist | 战报持久化 |
| economy.resource_changed | Economy | Gateway, Operation | 资源变更推送和积分 |
| economy.production_completed | Economy | Gateway | 生产完成推送 |

| social.alliance.created | Social | Gateway | 联盟创建通知 |
| social.diplomacy.changed | Social | Combat, Economy, Gateway | 外交变更影响战斗和贸易 |
| social.member.changed | Social | Gateway | 成员变更通知 |
| social.welfare.distributed | Social | Gateway, Economy | 联盟福利发放通知（Economy可能联动产出加成） |
| operation.season.phase_changed | Operation | 所有服务 | 赛季阶段切换，全局通知 |

| operation.game_event.expired | Operation | World, Economy, Gateway | 游戏事件过期，撤销效果 |
| config.reloaded | Config | 所有服务 | 配置热更通知 |

### 事件消息格式

```protobuf
message DomainEvent {
  string event_id = 1;          // 事件唯一ID（UUID）
  string event_type = 2;        // 事件类型（如 "combat.ended"）
  int64 timestamp = 3;          // 事件时间戳
  string aggregate_id = 4;      // 聚合根ID
  string publisher = 5;         // 发布服务名
  bytes payload = 6;            // 事件数据（按类型序列化）
  int32 version = 7;            // 事件版本号（兼容性）
}
```

### 事件版本兼容策略

DomainEvent的 `version` 字段标识事件Schema版本。配置热更或服务升级时事件Schema可能变化，兼容策略如下：

| 变更类型 | 兼容性 | 消费者处理 |
|---------|--------|-----------|
| 新增字段（Protobuf加字段） | 向前兼容 | 老消费者忽略未知字段，正常处理 |
| 删除字段（Protobuf删字段） | 向前兼容 | 老消费者读到默认值，需保证业务容忍默认值 |
| 修改字段语义 | 不兼容 | 必须升version，消费者按version分支处理 |
| 修改字段类型 | 不兼容 | 必须升version，新事件类型走新topic或新字段 |

**版本协商规则**：
- 发布者始终用最新version发布事件。
- 消费者声明自己支持的version范围，收到不支持的version时：①记录告警指标；②若高于支持范围则按"尽力解析"（忽略未知字段）或丢弃并告警。
- 不兼容变更走deprecation周期：旧version事件保留发布2个版本周期（消费者有升级窗口），之后只发新version。
- 事件Schema注册到Schema Registry（etcd），消费者启动时校验本地Schema与Registry一致。

### 事件投递保证

| 级别 | 说明 | 适用事件 |
|------|------|---------|
| 至少一次（at-least-once） | 消费者可能收到重复消息，需幂等处理。由Outbox+relay重试保证 | 所有领域事件 |
| 至多一次（at-most-once） | 消息可能丢失，不重试 | 聊天消息/非关键通知（可容忍丢失） |
| 效果上一次（effectively-once） | at-least-once + 消费者幂等去重，达到"只产生一次副作用"的效果 | 经济事件（资源操作不可重复）、战斗结算 |

**关于"恰好一次"**：分布式系统中不存在真正的恰好一次投递（网络分区/消费者崩溃无法保证）。业界共识是用"至少一次投递 + 消费者幂等"达到**效果上一次**——即消息可能重复投递，但重复处理不产生额外副作用。本文档统一使用"效果上一次"这一准确术语。

**幂等处理**：消费者记录已处理的event_id（写入去重表，TTL=事件有效期），重复事件直接丢弃；写操作依赖请求ID幂等（同一请求ID的重复请求返回相同结果，不重复变更资源）。

```
   │              │              │              │                    │

   │              │ 3.写入etcd    │              │                    │
   │              │──────────→ │              │                    │
   │              │              │              │                    │
   │              │              │ 4.etcd watch触发各服务              │
   │              │              │──────────→ │                    │
   │              │              │              │ 5.共享内核config    │
   │              │              │              │   reload本地缓存    │
   │              │              │              │ 6.触发业务层回调     │
   │              │              │              │──────────────────→ │
   │              │              │              │                    │ 7.按切换边界应用：
   │              │              │              │                    │   战斗:用旧配置快照
   │              │              │              │                    │   移动/生产:用新配置
   │              │ 8.发布config.reloaded事件                   │
   │              │──────────→ │(NATS广播)    │                    │
   │              │              │              │ 9.各服务确认已应用  │
   │ 10.热更完成通知│              │              │                    │
   │←────────── │              │              │                    │
```

**关键点**：Config Service只写etcd不直接调各服务（解耦）；各服务的共享内核config通过etcd watch被动感知变更（无需Config Service知道有哪些服务）；业务层按切换边界决定何时应用新配置（战斗中不切换，移动/生产立即切换，见[高可用设计.md](高可用设计.md)的"配置热更的业务切换边界"）。

### 配置热更的前置校验（缺口13）

配置热更前必须通过完整性与兼容性校验，校验失败拒绝热更：

| 校验层 | 校验内容 | 失败处理 |
|--------|---------|---------|
| JSON Schema | 每个配置文件符合Schema定义 | 拒绝，返回具体字段错误 |
| 引用完整性 | 配置间引用合法（如units引用的faction存在、combat引用的skill存在） | 拒绝，返回断链引用 |
| 配置包完整性 | 18个配置文件齐全、必需文件（game/units/buildings/resources/terrains/formulas）不缺失、依赖满足 | 拒绝，返回缺失文件清单 |
| 配置包兼容性 | 与存量数据Schema兼容（如新配置的resource_type覆盖存量玩家持有的资源类型、新配置的terrain_id覆盖存量地图格子） | 拒绝，返回不兼容项 |
| 自定义业务规则 | 各服务注册的业务约束校验（如战斗类型与阶段定义一致性、赛季阶段时间连续性） | 拒绝，返回违规规则 |

校验全部通过后Config Service才写入etcd，保证不合法配置不进入运行时。

### 跨服务配置一致性检查（缺口11）

配置热更后，各服务通过etcd watch独立感知变更并应用，但需保证所有服务最终都成功应用了新配置：

```
ConfigConsistencyChecker 流程：
  1. Config Service写入etcd（config_version=N+1）
  2. 各服务共享内核config watcher感知变更 → reload → 发布 config.reloaded 事件（含config_version+服务名）
  3. ConfigConsistencyChecker 收集各服务的 config.reloaded 确认
  4. 检查：所有在线服务是否都确认了 config_version=N+1？
     ├─ 全部确认 → 配置一致，热更完成
     └─ 有服务未确认 → 记录 config_reload_pending_count 指标，超阈值告警
```

**指标与告警**（详见[可观测性.md](可观测性.md)）：
- `config_reload_pending_count`：未确认最新配置的服务数量。>0持续超过阈值触发告警。
- `config_reload_duration`：各服务reload耗时，监控热更性能。
- `config_reload_success/failure_count`：reload成功/失败次数。

**业务切换边界保证时间差内不致错**：各服务应用新配置的时间差（<10秒）内，通过切换边界保证不致错——进行中战斗用开战时配置快照（不受热更影响）、移动/生产下个Tick用新配置（自然切换）。详见[高可用设计.md](高可用设计.md)的"配置热更的业务切换边界"。

> 每个业务服务执行功能时对其他服务的依赖系统梳理。依赖通过gRPC同步查询或NATS异步事件，避免循环依赖。

| Operation | 所有服务 | NATS异步 | 阶段切换 | 各服务调整行为（season.phase_changed事件） |

### 循环依赖验证

**Social ↔ Economy 的读操作循环**：Economy读Social（联盟加成），Social读Economy（福利发放资源）。
- **破解规则**：读操作允许双向（gRPC同步查询），写操作单向（通过事件异步，不反向调用）。
  - Economy→Social：gRPC读联盟加成（读操作，允许）
  - Social→Economy：通过 welfare.distributed 事件异步通知Economy发放资源（写操作，走事件不走gRPC，不形成同步循环）
- **权威方归属规则**：每个数据有唯一权威方——玩家属性权威方是Social，资源余额权威方是Economy。读操作可跨服务查权威方，写操作只在权威方执行后通过事件通知其他服务更新本地快照。保证无循环修改。

## 数据一致性策略

### 最终一致性

微服务间不使用分布式事务（性能不可接受），采用最终一致性：

| 场景 | 一致性策略 | 说明 |
|------|-----------|------|
| 战斗结果+战利品 | 事件驱动 | combat.ended事件触发经济系统发放战利品 |
| 联盟外交+贸易限制 | 事件驱动 | diplomacy.changed事件触发经济系统调整贸易 |
| 赛季阶段+全局限制 | 事件驱动 | season.phase_changed事件触发各服务调整行为 |
| 跨玩家交易 | Saga模式 | TradeOrder聚合协调双方确认，失败则补偿 |

### Saga模式示例（跨玩家交易）

```
交易流程：
  1. Economy创建TradeOrder（状态=待确认）
  2. 通知双方玩家确认
  3. 玩家A确认 → 扣减玩家A资源（状态=A已确认）
  4. 玩家B确认 → 扣减玩家B资源（状态=B已确认）
  5. 双方都确认 → 执行交换 → 完成

补偿流程（如果某步失败）：
  - 玩家A已扣减但玩家B拒绝 → 退还玩家A资源
  - 玩家A已扣减但超时 → 退还玩家A资源
  - 扣减失败 → 交易失败，不产生任何变更
```

**Saga补偿的可靠性保证**（补偿本身也可能失败，必须处理）：

| 机制 | 说明 |
|------|------|
| Saga日志持久化 | 每个Saga步骤（正向+补偿）写入`trade_saga_log`表，含步骤号、状态、补偿动作、重试次数 |
| 补偿重试 | 补偿失败时后台worker按指数退避重试（1s/2s/4s/8s/16s），最多重试5次 |
| 补偿幂等 | 补偿动作（如"退还玩家A资源"）携带saga_id+step_id幂等键，重复执行不重复退还 |
| 告警介入 | 重试5次仍失败的补偿，置为"需人工介入"状态，触发告警（见[可观测性.md](可观测性.md)），运营在管理后台手动处理 |
| 定期巡检 | 每小时巡检"需人工介入"的Saga，超24小时未处理升级告警 |

**为什么不能让补偿失败静默**：玩家A已扣减资源，若补偿（退还）失败且不处理，玩家A资源永久丢失。Saga日志+重试+告警保证补偿最终成功或人工兜底，资源不丢。

### 实体属性快照同步

跨服务需要访问的实体属性通过事件同步本地快照。**关键前提：明确属性的权威方归属，避免循环依赖**。

**属性权威方归属规则**：

| 属性类别 | 永久权威方 | 战斗中临时权威方 | 说明 |
|---------|-----------|----------------|------|
| 玩家基础属性（等级/经验） | Social | Social | 战斗中不修改，Social始终权威 |
| 兵种属性（攻防血量） | Social（配置+养成） | Combat（战斗中Buff修改） | 战斗中Combat临时权威，结束移交回Social |
| 资源余额 | Economy | Economy | 战斗中不修改（战利品战斗结束才发放） |
| 联盟科技加成 | Social | Social | 战斗中不修改 |
| 赛季Buff | Operation | Operation | 全局只读 |

**快照同步链路**（永久权威方 → 订阅方）：

```
Social Service（玩家属性永久权威方）
  │
  │  玩家属性变更（非战斗中）
  │  发布 player.attribute_changed 事件
  │
  ├─→ Combat Service：更新本地缓存的玩家属性快照
  │    （战斗开始时用此快照作为基线）
  │
  ├─→ Economy Service：更新本地缓存的玩家属性快照
  │    （生产公式可能引用玩家属性）
  │
  └─→ Gateway：推送给客户端
```

**战斗中属性修改的回流**（解决循环依赖）：

```
Combat Service（战斗中临时权威方）
  │
  │  战斗中Buff/伤害修改了兵种属性
  │  战斗中这些修改不实时同步（避免破坏战斗一致性）
  │
  │  战斗结束
  │  发布 combat.ended 事件（含最终属性变更）
  │
  └─→ Social Service：消费事件，将最终属性变更合并到永久权威方
       （此时Social恢复权威，Combat的临时权威结束）
```

**并发操作的权威方路由**：玩家在战斗中并发发起其他操作（如同时移动）时，其他服务读取的属性快照规则：

| 并发操作 | 读取的属性来源 | 一致性 |
|---------|--------------|--------|
| 移动（World） | 读Social的快照（非战斗修改的属性） | 移动不依赖战斗中变化的属性，安全 |
| 查询自身状态（Gateway） | 读Social快照 + Combat推送的战斗中变化 | 客户端看到战斗中实时变化 |
| 发起第二场战斗 | 读Social快照（不含第一场战斗中变化） | 短时战斗下可接受；长时战斗下第二场战斗开始时刷新 |

**快照一致性**：
- 非战斗属性：快照可能短暂过期（最终一致，<100ms）
- 战斗中属性：战斗期间冻结在Combat本地（保证战斗一致性）
- 战斗结束：通过 `combat.ended` 事件同步最终状态回Social，全局恢复一致
