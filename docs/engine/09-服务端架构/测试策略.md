# 测试策略

> 测试金字塔：单元测试（多）→ 集成测试（中）→ 契约测试（中）→ 端到端/混沌（少）。每层目标不同，不重复造轮子。

---

## 测试金字塔

```
        /\
       /  \        端到端/混沌工程（少，慢，高信心）
      /----\
     /      \      契约测试（服务间接口一致性）
    /--------\
   /          \    集成测试（服务内组件协作）
  /------------\
 /              \  单元测试（多，快，纯逻辑）
/----------------\
```

---

## 单元测试

**目标**：验证聚合根/领域服务/值对象的纯业务逻辑。不依赖外部（无DB/无MQ/无网络）。

| 测试对象 | 重点 | 工具 |
|---------|------|------|
| 聚合根 | 不变量维护、状态机流转、方法副作用 | go test + table-driven |
| 值对象 | 相等性、不可变性、校验 | go test |
| 领域服务 | 跨聚合的业务规则 | go test + mock仓储 |
| 规则引擎 | 条件评估、动作执行 | go test |
| 配置校验器 | 非法配置拒绝、合法配置通过 | go test |

**覆盖率要求**：domain层 ≥90%，application层 ≥80%，infrastructure层 ≥60%（依赖外部，难全覆盖）。

**示例**：

```go
func TestCombatAggregate_Start(t *testing.T) {
    tests := []struct{
        name    string
        combat  *Combat
        wantErr error
    }{
        {"正常开战", newCombat(状态=待战), nil},
        {"重复开战", newCombat(状态=进行中), ErrAlreadyStarted},
        {"无参战方", newCombat(状态=待战, 参战方=空), ErrNoParticipant},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            err := tt.combat.Start()
            assert.Equal(t, tt.wantErr, err)
        })
    }
}
```

## 集成测试

**目标**：验证服务内各层协作（application→domain→infrastructure），用testcontainers起真实依赖。

| 测试范围 | 依赖 | 工具 |
|---------|------|------|
| 仓储实现 | testcontainers起Redis/MySQL/MongoDB | go test + testcontainers |
| 事件总线 | testcontainers起NATS | go test + testcontainers |
| 投影器 | 起NATS+Redis，发事件验读模型更新 | go test |
| Outbox+relay | 起MySQL+NATS，验事件不丢 | go test |
| CQRS读写 | 起全栈，写后读验一致 | go test |

**关键集成测试**：
- Outbox原子性：写聚合根+写Outbox同事务，模拟中途崩溃，验事件不丢。
- 投影器最终一致：发事件后等读模型更新，验数据一致（带超时）。
- 跨区域聚合迁移：起两个World分片，触发跨区域移动，验聚合根归属切换。

## 契约测试

**目标**：防止服务间接口漂移。消费者定义期望的请求/响应，生产者验证自己满足契约。

| 契约对 | 工具 | 说明 |
|--------|------|------|
| gRPC接口 | buf + breaking检测 | CI检测proto变更是否破坏向后兼容 |
| 事件Schema | Schema Registry + 兼容检测 | 事件发布前检测Schema变更兼容性 |
| 消费者驱动契约 | Pact | 消费者写期望，生产者在CI验证 |

**gRPC契约**：用 `buf breaking` 在CI检测proto变更是否破坏现有调用方。禁止不兼容变更（改字段类型/删必需字段）直接合入，必须走deprecation。

**事件契约**：事件Schema注册到Schema Registry，发布者变更Schema前检测是否破坏消费者。新增字段允许（向前兼容），删字段/改语义需升version+deprecation周期。

## 端到端测试

**目标**：验证完整业务流程跨多服务正确流转。少量、高价值场景。

| 场景 | 验证 |
|------|------|
| 移动→触发战斗→结算→战利品→积分 | 完整事件链路，最终资源/积分正确 |
| 跨区域移动 | 聚合根迁移，最终位置正确 |
| 跨玩家交易Saga | 双方确认/补偿/超时各分支 |
| 赛季阶段切换 | 各服务响应阶段切换，行为正确 |
| 配置热更 | 热更后业务按切换边界应用新配置 |

**环境**：docker-compose起全栈（所有服务+依赖），用真实组件，不打mock。慢（分钟级），所以只跑关键路径，CI夜间跑或发版前跑。

## 混沌工程

**目标**：验证高可用设计在真实故障下生效。用Chaos Mesh注入故障。

| 故障注入 | 验证 | 频率 |
|---------|------|------|
| 杀Combat实例 | 战斗迁移到新实例，不丢战斗 | 每周 |
| 杀World分片主 | 备节点提升，该分片<5s恢复 | 每周 |
| 断NATS | Outbox积压，恢复后投递，事件不丢 | 每周 |
| 断Redis | 缓存降级，读穿透到DB，不崩 | 每月 |
| 网络延迟（gRPC） | 熔断触发，降级，不雪崩 | 每月 |
| 磁盘满 | 日志/Outbox写失败告警，不崩 | 每月 |
| 时钟漂移 | etcd选主异常检测 | 每季度 |

**稳态假设**：每次混沌实验前定义"稳态"（如战斗完成率>99.9%），注入故障后验证稳态保持。违反稳态则高可用设计有缺陷。

## 零硬编码静态扫描

> 保证服务端引擎代码中不出现任何游戏特定名词、数值常量、游戏特定枚举值。这是"引擎通用机制（换皮不改代码）"的前提保证。

### ZeroHardcodeScanner CI工具

| 项 | 说明 |
|----|------|
| 工具 | ZeroHardcodeScanner（自定义Go AST扫描器） |
| 触发 | 每次PR提交时CI强制运行 |
| 扫描范围 | `pkg/`（共享内核）+ 各服务的 `domain/` + `application/` 层（引擎通用代码） |
| 不扫描 | `infrastructure/`（技术实现，可含基础设施常量）+ `*_test.go`（测试可含具体值）+ 配置文件（配置本就是游戏特定内容） |

### 扫描规则

| 规则 | 说明 | 示例 |
|------|------|------|
| 无游戏特定名词 | 代码中不出现具体游戏名词（如"步兵""弓箭手""火球术""蚂蚁"） | `if unitType == "infantry"` 违规 |
| 无数值常量 | 代码中不出现魔法数字（除0/1/-1等边界值），数值必须从config查询 | `damage := 100`违规，`damage := config.GetBaseDamage()`合规 |
| 无游戏特定枚举 | 不硬编码游戏特定枚举值，枚举由配置定义 | `if faction == "ants"`违规，`if faction == config.GetFactionID("ants")`合规 |
| 扩展点显式注册 | 所有配置查询走ConfigQueryAPI，不直接读配置文件 | 直接`json.Unmarshal(configFile)`违规 |

### 白名单

| 允许 | 理由 |
|------|------|
| 框架基础设施常量（默认超时30秒、默认重试3次、默认分片数等） | 与游戏无关的基础设施参数 |
| 0/1/-1等边界值 | 逻辑边界，非游戏数值 |
| 数学常数（PI、E等） | 数学运算需要 |

### CI门禁

零硬编码扫描为**CI强制检查项**，扫描发现违规项阻止合入。违规报告含：文件路径+行号+违规内容+建议修复方式（改为从config查询）。

## 游戏包与扩展边界验证

> 用昆虫世界和一个最小第二用例验证稳定契约。允许题材扩展，但领域模块与通用内核不得依赖游戏包。

### ReskinValidator

| 项 | 说明 |
|----|------|
| 工具 | ReskinValidator（换皮验证器） |
| 触发 | 发布前强制检查+夜间回归 |
| 验证题材 | 昆虫世界最小包 + 一个最小第二用例包 |

### 验证内容

```
ReskinValidator 流程：
  for each 测试游戏包:
    1. 按 manifest 加载该包启用模块所需的配置
    2. 配置校验（JSON Schema+引用完整性+完整性+兼容性）
    3. 启动服务端（所有服务用该配置包初始化）
    4. 执行核心功能用例（见下）
    5. 验证用例通过；领域模块与通用内核无题材依赖
    6. 停止服务端，清理
```

### 验证用例（核心功能在三题材下均正常运行）

| 用例 | 验证内容 |
|------|---------|
| 移动用例 | 实体按该题材的移动规则移动，路径/消耗/视野正确 |
| 战斗用例 | 战斗按该题材的战斗公式/技能/阵型/克制结算，结果正确 |
| 经济用例 | 生产/采集/交易按该题材的经济规则执行，资源流转正确 |
| 联盟用例 | 联盟创建/外交/福利按该题材的权限映射执行，权限正确 |
| 赛季用例 | 赛季阶段/重置/继承/奖励按该题材的赛季规则执行，流转正确 |
| 事件用例 | 游戏事件按该题材的事件定义触发/执行/过期，效果正确 |

### 通过标准

- 3个题材配置包均通过配置校验
- 3个题材下核心功能用例全部通过
- 整个验证过程**未修改任何引擎代码**（git diff pkg/ + domain/ + application/ 为空）
- 验证报告含：各题材各用例的通过/失败状态+失败原因

### CI门禁

换皮通用性验证为**发布前强制检查项**，验证失败阻止发版。夜间回归验证失败告警但不阻塞日常开发。

## 测试数据

| 类型 | 说明 |
|------|------|
| 单元测试 | 代码内构造，不依赖外部数据 |
| 集成测试 | testcontainers起空库，测试内seed |
| 端到端 | 固定fixture（玩家/联盟/地图初始数据），可重置 |
| 压测 | 从生产脱敏采样（真实分布），仅压测环境 |

**数据隔离**：每个测试用独立namespace/数据库前缀，并行不干扰。测试结束清理。

## CI集成

| 阶段 | 跑什么 | 门禁 |
|------|--------|------|
| PR提交 | 单元测试+lint+buf breaking检测 | 全过才可合入 |
| 合入主干 | 单元+集成+契约 | 全过才可部署 |
| 部署前 | 端到端 | 全过才可发版 |
| 夜间 | 端到端+混沌 | 失败告警，不阻塞 |
| 发版前 | 全量+混沌 | 全过才可发版 |
