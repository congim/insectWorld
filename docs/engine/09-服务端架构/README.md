> 状态：现行入口
>
> 总体决策：限界上下文清晰，模块化单体优先，按证据演进为独立服务。

完整目标见[目标架构](../../architecture/目标架构.md)，当前目录与目标映射见[当前代码地图](../../architecture/当前代码地图.md)。本目录中的专题文档提供详细约束，不再用固定服务数量定义系统。

## 逻辑结构

```text
客户端
  ↓
接入层：连接、鉴权、限流、协议适配
  ↓
应用层：用例编排、权限、事务与幂等协调
  ↓
领域上下文：Identity / World / Growth / Combat / Economy / Social / LiveOps ...
  ↓
基础设施适配：数据库、缓存、事件、配置、观测
```

每个上下文遵循：

```text
interfaces → application → domain ← infrastructure
```

目录是逻辑边界，部署是运行决策。首个闭环默认使用 gateway、game、control 三个进程单元；只有独立扩缩容、故障隔离、资源竞争或发布节奏有证据时才拆服务。

## 架构硬约束

- domain 零基础设施依赖，application 不直接依赖 infrastructure；
- 一个业务表只有一个上下文拥有写权限；
- 单上下文内优先本地事务，跨上下文默认 Outbox + 幂等事件；
- 配置、事件、协议和存储 schema 必须显式版本化；
- 运行中战斗等长事务绑定创建时的配置版本；
- 题材内容只进入游戏包或扩展，不进入领域模块；
- 任何独立服务提案必须通过 ADR 说明收益、代价与迁移路径。

## 技术选型原则

当前代码或旧文档出现某个中间件，不代表永久冻结。技术选型必须从一致性、延迟、吞吐、可运维性和团队成本出发，并有最小验证。首个闭环优先使用简单、可本地运行和可自动测试的实现。

## 实现状态

仓库已有多个 Go module、DDD 骨架、配置/公式/规则能力和部分领域实现，但成熟度不一。是否完成以自动化测试和可运行链路为准，不能根据目录或 proto 是否存在判断。
