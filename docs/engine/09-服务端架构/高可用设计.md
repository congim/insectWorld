# 高可用设计

> 不允许任何单点存在。每个组件必须可水平扩展或有主备故障转移机制。

---

## 无单点架构清单

| 组件 | 方案 | 高可用机制 | 故障影响 |
|------|------|-----------|---------|
| Load Balancer | Nginx/HAProxy双机VRRP | 主备自动切换 | 单台挂了备机接管，<1秒 |
| Gateway | 多实例无状态 | LB负载均衡，实例挂了流量转移 | 连接断开，客户端重连到其他实例 |
| World Service | 多实例+分片 | 每分片主备，主挂了备接管 | 该分片短暂不可用（<3秒） |
| Combat Service | 多实例 | 战斗ID路由，实例挂了战斗迁移 | 进行中的战斗按平局结算 |
| Economy Service | 多实例+分片 | 按玩家ID分片，每片主备 | 该分片短暂不可用 |
| Social Service | 多实例+分片 | 按联盟ID分片，每片主备 | 该分片短暂不可用 |
| Operation Service | 主备选举 | etcd选主，主挂了备接管 | 赛季操作短暂延迟 |
| Config Service | 多实例无状态 | 配置存etcd，任意实例可服务 | 无影响 |
| Persist Service | 多实例无状态 | 任务队列驱动，任意实例可消费 | 无影响 |
| NATS消息队列 | 3+broker集群 | Raft选主，副本机制 | 单broker挂了不影响消息 |
| etcd服务发现 | 3+节点集群 | Raft强一致 | 单节点挂了集群仍可用 |
| Redis Cluster | 6+节点（3主3从） | 分片+副本+自动故障转移 | 单节点挂了对应分片从接管 |
| MySQL | 每分片1主2从 | 半同步复制+自动切换 | 主挂了从提升为主 |
| MongoDB | 3+节点Replica Set | OpLog复制+选举 | 主挂了从选举新主 |

## 分片策略

### 分片维度选择

| 服务 | 分片维度 | 分片函数 | 理由 |
|------|---------|---------|------|
| World Service | 地图区域ID | hash(region_id) % N | 同一区域的地图/移动操作在同一实例，避免跨实例 |
| Combat Service | 战斗ID | hash(combat_id) % N | 一场战斗的完整流程在同一实例 |
| Economy Service | 玩家ID | hash(player_id) % N | 同一玩家的资源操作在同一实例，避免分布式事务 |
| Social Service | 联盟ID | hash(alliance_id) % N | 同一联盟的操作在同一实例 |
| Operation Service | 不分片（全局单例主备） | 无 | 同时只有一个活跃赛季，全局规则/事件需单一权威方，按赛季ID分片无意义；采用etcd选主主备模式 |

### 分片路由

```
客户端请求 → Gateway → 根据操作类型确定分片键 → 路由到对应分片实例
```

| 操作 | 分片键 | 路由到 |
|------|--------|--------|
| 移动实体 | 实体所在区域ID | World Service对应分片 |
| 发起战斗 | 新生成的战斗ID | Combat Service任意实例 |
| 资源操作 | 玩家ID | Economy Service对应分片 |
| 联盟操作 | 联盟ID | Social Service对应分片 |
| 赛季/全局事件操作 | 无（全局单例） | Operation Service主节点 |

### 跨分片操作处理

部分操作需要跨分片，处理策略：

| 场景 | 跨分片原因 | 处理策略 |
|------|-----------|---------|
| 跨区域移动 | 实体从区域A移到区域B | 区域A发布`movement.cross_region`事件，区域B消费并接管 |
| 跨联盟外交 | 联盟A对联盟B宣战 | 联盟A发布`diplomacy.proposed`事件，联盟B消费并确认 |
| 跨玩家交易 | 玩家A与玩家B交易 | 创建TradeOrder聚合，双方确认后执行，Saga模式保证一致性 |
| 联盟战 | 多联盟多玩家参战 | Combat Service独立分片，参战方属性通过事件快照同步 |

### 分片 rebalance 流程

扩容或负载不均触发重新分片时，采用**双写过渡**保证迁移期间不丢数据、不中断服务：

```
rebalance流程（以World Service为例，新增分片N+1）：
  1. 计算迁移计划：哪些区域从现分片迁到新分片N+1
  2. 新分片N+1启动并加入服务发现，开始接收新区域的路由
  3. 双写过渡期（持续30秒）：
     ├─ 写操作：同时写源分片和目标分片（目标分片为副本次要写）
     └─ 读操作：仍读源分片（目标分片数据可能不全）
  4. 数据校验：对比源分片与目标分片的关键数据（实体位置/移动状态），一致后进入切换
  5. 切换路由：Gateway路由表更新，新区域请求路由到目标分片N+1
  6. 源分片只读期（持续60秒）：源分片降级为只读（处理迁移中的残留请求），目标分片接管读写
  7. 确认下线：源分片无流量后，清理迁移区域的数据，rebalance完成
```

**一致性保证**：双写过渡期保证迁移中写入不丢（即使切换中途有请求仍能落到目标分片）；数据校验保证切换前目标分片数据完整；源分片只读期兜底处理迁移中的边界请求。整个rebalance对玩家透明，仅迁移瞬间可能有<100ms的"迁移中"提示。

## 故障转移机制

### 有状态服务故障转移

```
正常状态：                     主节点故障：
┌──────┐  ┌──────┐           ┌──────┐  ┌──────┐
│主节点 │  │备节点 │           │  X   │  │备节点 │
│(读写) │  │(同步) │           │      │  │(提升) │
└──┬───┘  └──┬───┘           └──────┘  └──┬───┘
   │         │                           │
   └─OpLog──→│           etcd检测到主挂了  │
                            │              │
                            └─选举────────→│
                                           │
                            备节点提升为主  │
                            开始接受读写    │
```

| 步骤 | 耗时 | 说明 |
|------|------|------|
| 主节点故障 | 0s | 心跳超时检测 |
| etcd检测 | 3s | 心跳间隔3秒，3次未响应判定故障 |
| 选举新主 | 1s | Raft选举 |
| 状态恢复 | <1s | 从OpLog/Redis同步恢复 |
| 总恢复时间 | <5s | 从故障到恢复 |

### Combat Service特殊处理

战斗服务实例故障时，进行中的战斗不能直接丢失，**优先迁移到其他实例继续执行**：

| 策略 | 说明 |
|------|------|
| 战斗状态持久化 | 每轮结束将战斗状态写入Redis（异步，<50ms） |
| 故障检测 | Gateway/服务发现检测到Combat实例挂了（<3s） |
| 战斗迁移（优先） | 从Redis恢复战斗状态到新实例，继续执行剩余轮次 |
| 客户端提示 | 迁移期间向参战方推送"战斗恢复中"，避免玩家以为卡死 |
| 迁移超时兜底 | 30秒内无法恢复（如Redis状态损坏），才按平局结算并退还双方投入 |

**为什么30秒而非5秒**：战斗是玩家高价值场景，平局结算对体验伤害大。30秒覆盖一次Redis故障切换（<5s）+实例调度启动（<10s）+状态反序列化（<2s），正常情况下迁移在10秒内完成；仅当状态确实损坏才结算。结算时全额退还双方投入资源，避免玩家因服务器故障受损。

### Gateway故障处理

Gateway无状态，故障处理最简单：

| 步骤 | 说明 |
|------|------|
| LB健康检查 | 每5秒检查Gateway实例健康 |
| 故障摘除 | 不健康实例从LB摘除 |
| 连接转移 | 客户端检测断线，重连到其他Gateway实例 |
| 状态恢复 | 从Redis恢复玩家会话状态 |

**Gateway连接状态存储策略**（避免Redis瓶颈）：

| 数据 | 存储方式 | 理由 |
|------|---------|------|
| 连接存活标记 | Gateway本地内存 | 仅本实例需要知道连接是否存活，无需共享 |
| 玩家→Gateway路由 | Redis（仅玩家ID→实例ID映射） | 重连时定位原实例；写入频率低（仅上线/重连时写） |
| 玩家会话快照 | Redis（仅在线时存） | 故障恢复用；5分钟无操作过期清理 |
| 心跳/位置等高频状态 | Gateway本地内存 + 批量异步刷Redis | 避免每秒10万次Redis写；本地内存命中，每10秒批量同步一次 |

**容量评估**：10万连接，玩家→Gateway路由10万条Redis KV（<100MB），会话快照10万条（<1GB，5分钟过期），高频状态本地内存（单实例1万连接×2KB=20MB）。Redis QPS从"10万/秒"降到"1万/秒"（仅上线/重连/批量同步），消除瓶颈。

| Economy Service | 2核 | 4G | 10,000玩家 | Redis IO |
| Social Service | 2核 | 4G | 5,000联盟 | MySQL IO |

### 扩容策略

| 指标 | 阈值 | 动作 |
|------|------|------|
| Gateway CPU > 70% | 持续1分钟 | 新增Gateway实例 |
| World Service 分片负载不均 | 持续5分钟 | 重新分片（rebalance） |
| Combat Service 排队 > 100 | 持续1分钟 | 新增Combat实例 |
| Economy Service Redis内存 > 80% | 持续5分钟 | 扩容Redis或清理冷数据 |
| 任何服务错误率 > 1% | 立即 | 告警 + 自动扩容 |

### 目标SLA

**可用性SLA**（服务是否可访问）：

| 指标 | 目标 | 保障措施 |
|------|------|---------|
| 可用性 | 99.95%（月停机<22分钟） | 无单点+自动故障转移 |
| 请求延迟P99 | <100ms | 分片+缓存+本地化 |
| 战斗结算延迟 | <500ms | Combat Service独立分片 |
| 移动同步延迟 | <50ms | World Service本地计算 |
| 配置热更生效 | <10秒 | etcd watch + 事件广播 |

**业务正确性SLA**（服务可用时业务结果是否正确，覆盖"软停机"场景）：

| 指标 | 目标 | 覆盖的软停机场景 | 保障措施 |
|------|------|----------------|---------|
| 战斗结果正确率 | 99.99% | Combat故障迁移期间不丢战斗、不误结算 | 战斗状态Redis持久化+迁移优先+30秒兜底 |
| 资源操作准确率 | 99.999% | Economy事件不丢不重 | Outbox保证至少一次+幂等去重 |
| 跨区域移动完成率 | 99.99% | 分片rebalance/聚合迁移期间移动不丢 | 双写过渡+聚合根迁移幂等 |
| 配置热更一致性 | 99.9% | 热更切换瞬间业务用旧配置不致错 | 配置版本号+业务切换边界（见下） |
| 赛季阶段切换正确率 | 99.99% | Operation主备切换期间阶段不重复/不跳 | etcd选主+阶段流转幂等 |

**配置热更的业务切换边界**：运行中的业务用旧配置还是新配置，按场景区分：

| 业务场景 | 切换策略 | 理由 |
|---------|---------|------|
| 进行中的战斗 | 用开战时配置快照，战斗结束后新战斗用新配置 | 战斗中切换配置会破坏伤害计算一致性 |
| 进行中的移动 | 用当前最新配置 | 移动是连续过程，切换影响小 |
| 生产/采集 | 下个Tick用新配置 | 离散计算，自然切换 |
| 联盟外交状态 | 用当前最新配置 | 状态查询为主，切换无副作用 |

## 优雅停机

每个服务实现优雅停机流程：

```
收到SIGTERM
  │
  ├─ 1. 从服务发现注销（不再接受新请求）
  │
  ├─ 2. 停止接受新连接/新消息
  │
  ├─ 3. 等待当前处理中的请求完成（超时30秒）
  │
  ├─ 4. 如果是有状态服务：
  │    ├─ 将内存状态持久化到Redis/DB
  │    └─ 通知备节点接管
  │
  ├─ 5. 如果是Gateway：
  │    ├─ 通知所有连接的客户端"服务器即将重启"
  │    └─ 等待客户端重连到其他实例
  │
  └─ 6. 关闭数据库/缓存/消息队列连接，进程退出
```
