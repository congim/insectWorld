# ADR-003 规则动作枚举口径统一：以E2已实现代码为权威事实

> **状态**：已接受（Accepted）
> **日期**：2026-08-11
> **决策者**：程基岩（engineering-lead）
> **关联**：《通用SLG框架设计书》3.8.2 动作类型契约；`docs/engine/02-技术架构/03-规则系统.md` `rule_definitions`/`rule_actions` 契约；ADR-002（E2 行为注册表）；E1 公式引擎（`execute_formula` 依赖，已冻结）
> **被依赖**：E14 存量功能接入（`execute_formula` 存量功能候选）、E16 题材扩展（信息素/进化树走注册表）
> **替代**：本 ADR 修订《通用SLG框架设计书》3.8.2 与《03-规则系统.md》的动作类型枚举口径，以本 ADR 为统一权威规格

### 1.3 分歧本质

1. **枚举数量与成员不一致**：设计书 7 个 vs 03-规则系统.md 8 个，仅 3 个（apply_buff/remove_buff/spawn_entity）三方共有；03-规则系统.md 有 5 个专属项（modify_attribute/grant_resource/send_event/execute_formula/custom），设计书有 4 个专属项（modify_resource/trigger_combat/send_notify/change_terrain）。
2. **与已实现代码不一致**：03-规则系统.md 的枚举与 E2 已落地代码不符；设计书的列表恰好与 E2 代码一致。
3. **可扩展性语义矛盾**：设计书约束"动作类型不可配置（需要新类型必须扩展框架代码）"与 ADR-002/E2 已实现的行为注册表矛盾——E2 已实现"题材层新动作 = `init()` 注册，框架零改动"。

## 二、决策

**以 E2 已实现代码为权威事实：统一动作枚举 = 内置动作（7 个，与 E2 代码一致）+ 注册表可扩展（execute_formula 列为内置动作候选，本期不内置）。**

### 2.1 统一动作枚举：内置动作（7 个）

| 动作类型 | 参数契约（action_params） | E2 端口调用 | 实现文件 |
|----------|---------------------------|-------------|----------|
| apply_buff | {buff_id, target} | Accessor.ApplyBuff | action_apply_buff.go |
| remove_buff | {buff_id, target} 或 {source_tag, target} | Accessor.RemoveBuff / RemoveBuffByTag | action_remove_buff.go |
| modify_resource | {resource_id, amount, target} | Accessor.ModifyResource | action_modify_resource.go |
| spawn_entity | {template_id, position{x,y}, owner} | Accessor.SpawnEntity | action_spawn_entity.go |
| trigger_combat | {attacker_id, defender_id} | Accessor.TriggerCombat | action_trigger_combat.go |
| send_notify | {msg_id, target, params} | Accessor.SendNotify | action_send_notify.go |
| change_terrain | {position{x,y}, terrain_id} | Accessor.ChangeTerrain | action_change_terrain.go |

### 2.2 旧枚举映射说明

| 03-规则系统.md 旧枚举 | 处理 | 说明 |
|------------------------|------|------|
| apply_buff / remove_buff / spawn_entity | 保留（内置） | 与 E2 代码一致 |
| modify_attribute | 移除，**归入 buff 体系** | 属性修改统一表达为"挂载/移除 Buff"（apply_buff/remove_buff），不单独设动作类型 |
| grant_resource | 移除，**由 modify_resource 覆盖** | 同语义：发放/扣减资源；E2 端口为 `ModifyResource(amount)`，amount 为正加、为负扣 |
| send_event | 移除，**由 send_notify 覆盖** | 通知/事件下发统一走 send_notify（目标 + msgID + 参数） |
| custom | 保留为"**题材层注册的动作类型标识**" | **非内置动作**。实际类型是题材层注册的具体标识（如 release_pheromone），静态 schema 无法枚举题材类型，故保留 custom 作为占位标记；运行时以 ActionRegistry 为准（配置引用未注册类型 → 启动全量校验拒绝） |
| execute_formula | 列为**内置动作候选**（见 2.3） | 依赖 E1 公式引擎（已冻结） |

### 2.3 execute_formula 决策

**决策：本期先不加为内置动作，标注为"题材层可注册示例"；E14 存量功能接入时再评估内置。**

理由：

- **无消费方（YAGNI，规范 4.5）**：当前 12 个存量功能与 P3 六骨头均无"规则动作内直接执行公式"的消费场景；E1 公式引擎已冻结，但动作侧接口尚未冻结，贸然内置等于为一个没有消费者的功能维护契约。
- **E2 代码事实**：ADR-002 已将 execute_formula 列为"依赖 E1 接口冻结，本期可选"，E2 落地时未实现——内置动作列表以代码为准，execute_formula 不在其中。
- **题材层可注册**：若某题材确实需要"动作内算公式"，可先在题材层实现 RuleActionHandler 并注册（示例动作），框架零改动；待 E14 存量功能接入时若成为通用需求，再升级为内置动作并补端口方法。

> 注：配置若引用 execute_formula，必须由题材层注册对应 handler，否则启动全量校验拒绝启动（未注册动作类型）。

### 2.4 与行为注册表的关系

动作类型列表**不再是"固定枚举"**，而是：

> **动作类型 = 内置动作（7 个，与 E2 代码一致） + 注册表可扩展（题材层 init() 注册）**

- "动作类型不可配置（需要新类型必须扩展框架代码）" 修订为："**新类型 = 注册表注册**（内置 7 个直接可用，新类型由题材层 `init()` 注册，框架代码零改动）"。
- 权威事实链：**E2 代码（action_registry.go + 7 动作文件）→ 本 ADR → 设计书 3.8.2 / 03-规则系统.md**。文档仅描述契约，运行时以 `ActionRegistry` 启动全量校验为准。
- `rule_definitions`/`rule_actions` 契约中 action_type 的**静态 schema 枚举降级为提示性**：枚举列出内置 7 个 + custom（占位）+ execute_formula（候选标注）；运行时权威校验 = `ValidateTypes`（配置引用未注册类型拒绝启动）。

## 四、备选方案对比

| 方案 | 说明 | 评估 | 结论 |
|------|------|------|------|
| A. 以 03-规则系统.md 的 8 枚举为权威 | 按旧枚举重写 E2 代码与端口（新增 modify_attribute/grant_resource/send_event/execute_formula/custom 五个动作） | 与已落地代码背道而驰，5 个专属项中多数无消费方（YAGNI）；重构已验收的 E2 代码，成本高、收益为零 | 否决 |
| B. 以设计书为权威但保留"不可配置"约束 | 仅采信设计书 7 个列表，保留"新类型必须扩展框架代码" | 与 ADR-002/E2 已实现的注册表机制直接矛盾，题材扩展被迫回退到改框架 | 否决 |
| C. 以 E2 代码为权威 + 注册表可扩展语义（选定） | 内置 7 个（与代码一致）+ custom 保留占位 + execute_formula 列为候选；文档降级为契约描述，运行时以注册表校验为准 | 与已验收代码零冲突；文档口径统一；题材扩展语义正确；execute_formula 按 YAGNI 延后内置 | ✅ 选定 |
