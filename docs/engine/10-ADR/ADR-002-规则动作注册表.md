# ADR-002 规则动作注册表：RuleActionHandler 行为注册表 + 启动全量校验

> **状态**：已接受（Accepted）
> **日期**：2026-08-11
> **决策者**：程基岩（engineering-lead）
> **关联**：《通用SLG服务端开发计划》P1-E2；《通用SLG框架设计书》3.8 规则系统动作类型契约；`server/shared/pkg/rule/rule.go`（现有规则引擎）；`docs/engine/02-技术架构/03-规则系统.md`；`docs/engine/06-扩展指南/扩展接口.md`
> **依赖**：E1 公式引擎（`execute_formula` 动作引用公式引擎，本期可选）
> **被依赖**：E5 存量功能注册表化、E16 题材扩展（信息素/进化树走注册表）

---

## 一、背景与问题

### 1.1 现状

| 事实 | 位置 | 说明 |
|------|------|------|
| 动作类型写死枚举 | 设计书 3.8.2 动作类型契约 | 契约声明动作类型"**不可配置**"，框架固定 7 种：`apply_buff / remove_buff / modify_resource / spawn_entity / trigger_combat / send_notify / change_terrain`；"需要新动作类型必须扩展框架代码" |
| 现有注册表只到"规则级" | `server/shared/pkg/rule/rule.go` | 只有 `RuleRegistry`（扩展点ID → `RuleExecutor`），管"一条规则由谁执行"，**没有动作级注册机制** |
| 文档口径分裂 | 03-规则系统.md 的 `rule_definitions`/`rule_actions` 契约 | `action_type` 枚举写死为 `apply_buff/remove_buff/modify_attribute/grant_resource/spawn_entity/send_event/execute_formula/custom`，与设计书 3.8 的 7 种不一致 |

### 1.2 评审结论

《通用SLG框架设计评审报告》**扩展机制缺失**：动作类型写死枚举，题材层（昆虫"信息素""进化树"）新增动作时被迫修改框架代码，违反"换皮=换肉，骨头不动"；若 E1/E2 不做，P3 六骨头与 E14 存量功能会各自发明扩展方式，产生**两套扩展机制**。

《通用SLG服务端开发计划》将行为注册表列为 **P1-E2（先于 P3）**：新增 `server/shared/pkg/rule/action_registry.go`（`RuleActionHandler` 接口 + `Register` + 启动全量校验），7 内置动作拆独立文件 `init()` 注册；题材层新动作 `blank import`，**框架零改动**。

---

## 二、决策

**采用：RuleActionHandler 行为注册表 + init() 注册 + 启动全量校验。**

四个组成部分：

1. 新增 `server/shared/pkg/rule/action_registry.go`：`RuleActionHandler` 接口、`ActionContext`、`ActionAccessor` 端口、`ActionRegistry` 注册表、包级全局注册函数 `RegisterAction`、启动校验 `ValidateTypes`；
2. 7 个内置动作拆分到 `rule` 包内**独立文件**（`action_apply_buff.go` 等），各自 `init()` 注册；
3. 题材层新增动作 = 在题材包实现 `RuleActionHandler`，`init()` 调 `rule.RegisterAction`，服务入口 `blank import` 题材包即可生效，**框架代码零改动**；
4. 启动时对配置引用的全部 `action_type` 做**全量校验**，未注册则拒绝启动。

## 三、设计要点

### 3.1 RuleActionHandler 接口

```go
// RuleActionHandler 规则动作处理器，注册到ActionRegistry后由规则引擎按动作类型分发调用。
// 每个动作类型全局唯一（Type()返回值），题材层新动作实现本接口并注册，框架零改动。
type RuleActionHandler interface {
	// Type 返回动作类型标识，如"apply_buff"，作为注册与配置引用的唯一key。
	Type() string
	// Execute 执行动作，基于ActionContext执行并写入结果；返回错误时由调用方记录并跳过后续动作。
	Execute(ctx ActionContext) error
}
```

### 3.2 ActionContext 结构

```go
// ActionContext 规则动作执行上下文，封装触发上下文、动作参数与结果写入。
// 由规则引擎在执行动作前构造，同一规则内的多个动作共享一份上下文。
type ActionContext struct {
	RuleID    string         // 规则ID，用于日志与审计关联
	EventName string         // 触发事件名，如"on_combat_start"
	Input     map[string]any // 触发上下文变量（attacker/defender/terrain等），由事件源提供
	Params    map[string]any // 动作参数，来自配置action_params，字段含义由各动作契约定义
	Output    map[string]any // 结果写入区，动作副作用（如生成的实体ID）写回供后续动作与审计使用
	Accessor  ActionAccessor // 领域服务访问端口，由宿主服务实现并注入，动作经此操作实体/资源/Buff等
}
```

### 3.3 ActionAccessor 端口（共享内核 → 服务适配）

共享内核 `rule` 包不能 import 各服务 domain（依赖方向约束），因此定义 `ActionAccessor` 端口接口，由宿主服务实现并注入 `ActionContext.Accessor`。7 个内置动作是"**薄处理器**"，真正的副作用经端口调用服务侧实现（端口-适配器模式）。

```go
// ActionAccessor 动作访问端口，由宿主服务实现并注入ActionContext，
// 使共享内核的动作处理器不依赖任何服务domain实现（端口-适配器模式，符合DDD依赖方向）。
type ActionAccessor interface {
	// ApplyBuff 给目标实体挂载Buff。
	ApplyBuff(ctx ActionContext, target string, buffID string) error
	// RemoveBuff 按BuffID移除目标实体上的Buff。
	RemoveBuff(ctx ActionContext, target string, buffID string) error
	// RemoveBuffByTag 按来源标记批量移除目标实体上的Buff。
	RemoveBuffByTag(ctx ActionContext, target string, sourceTag string) error
	// ModifyResource 修改目标资源余额，amount为正增加、为负扣减（int64，AGENTS.md规范8）。
	ModifyResource(ctx ActionContext, target string, resourceID string, amount int64) error
	// SpawnEntity 按模板生成实体，返回生成的实体ID。
	SpawnEntity(ctx ActionContext, templateID string, posX int32, posY int32, owner string) (int64, error)
	// TriggerCombat 触发一场战斗。
	TriggerCombat(ctx ActionContext, attackerID string, defenderID string) error
	// SendNotify 向目标发送通知消息。
	SendNotify(ctx ActionContext, target string, msgID string, params map[string]any) error
	// ChangeTerrain 修改指定位置的地形。
	ChangeTerrain(ctx ActionContext, posX int32, posY int32, terrainID string) error
}
```

### 3.4 注册机制

与现有 `RuleRegistry` 风格对齐：`Register` 校验 Type() 非空、handler 非 nil、不重复注册返回错误。差异点：为支持 `init()`（blank import）注册，提供**包级全局注册表 + RegisterAction**。

```go
// ActionRegistry 动作注册表，管理动作类型到处理器的映射。
// 规则引擎执行规则时按action_type查询处理器，未注册的动作类型返回错误。
type ActionRegistry struct {
	handlers map[string]RuleActionHandler // 动作类型到处理器的映射，key为Type()返回值
}

// NewActionRegistry 创建动作注册表实例。
func NewActionRegistry() *ActionRegistry {
	return &ActionRegistry{handlers: make(map[string]RuleActionHandler)}
}

// Register 注册动作处理器，Type()为空、handler为nil或重复注册返回错误。
func (r *ActionRegistry) Register(handler RuleActionHandler) error {
	if handler == nil {
		return fmt.Errorf("动作处理器不能为空")
	}
	actionType := handler.Type()
	if actionType == "" {
		return fmt.Errorf("动作类型不能为空")
	}
	if _, exists := r.handlers[actionType]; exists {
		return fmt.Errorf("动作类型 %s 已注册，禁止重复注册", actionType)
	}
	r.handlers[actionType] = handler
	return nil
}

// Get 查询动作处理器，未注册时返回错误。
func (r *ActionRegistry) Get(actionType string) (RuleActionHandler, error) {
	handler, exists := r.handlers[actionType]
	if !exists {
		return nil, fmt.Errorf("动作类型 %s 未注册处理器", actionType)
	}
	return handler, nil
}

// Types 返回全部已注册的动作类型，用于启动全量校验与诊断输出。
func (r *ActionRegistry) Types() []string {
	types := make([]string, 0, len(r.handlers))
	for actionType := range r.handlers {
		types = append(types, actionType)
	}
	return types
}

// globalActionRegistry 全局动作注册表，供各包init()注册（blank import扩展）。
var globalActionRegistry = NewActionRegistry()

// RegisterAction 全局注册动作处理器，供init()调用。
// 注册失败（重复/空类型）属于编程错误，panic让进程在启动期失败，符合"启动全量校验"原则。
func RegisterAction(handler RuleActionHandler) {
	if err := globalActionRegistry.Register(handler); err != nil {
		panic("规则动作注册失败: " + err.Error())
	}
}

// GlobalActionRegistry 返回全局动作注册表，规则引擎启动时获取并注入校验器。
func GlobalActionRegistry() *ActionRegistry { return globalActionRegistry }

// ValidateTypes 启动全量校验：检查配置引用的动作类型是否全部已注册，返回缺失类型列表。
// 非空时服务拒绝启动——配置引用未注册动作=配置错误，越早暴露越好。
func ValidateTypes(configuredTypes []string) []string {
	registered := globalActionRegistry.Types()
	regSet := make(map[string]struct{}, len(registered))
	for _, actionType := range registered {
		regSet[actionType] = struct{}{}
	}
	var missing []string
	for _, actionType := range configuredTypes {
		if _, ok := regSet[actionType]; !ok {
			missing = append(missing, actionType)
		}
	}
	return missing
}
```

### 3.5 7 个内置动作拆分方案

在 `rule` 包内独立文件，每个文件一个动作 + `init()` 注册：

| 文件 | 动作类型 | 参数契约（action_params） | 端口调用 |
|------|----------|---------------------------|----------|
| action_apply_buff.go | apply_buff | `{buff_id, target}` | `Accessor.ApplyBuff` |
| action_remove_buff.go | remove_buff | `{buff_id, target}` 或 `{source_tag, target}` | `Accessor.RemoveBuff` / `Accessor.RemoveBuffByTag` |
| action_modify_resource.go | modify_resource | `{resource_id, amount, target}` | `Accessor.ModifyResource` |
| action_spawn_entity.go | spawn_entity | `{template_id, position{x,y}, owner}` | `Accessor.SpawnEntity` |
| action_trigger_combat.go | trigger_combat | `{attacker_id, defender_id}` | `Accessor.TriggerCombat` |
| action_send_notify.go | send_notify | `{msg_id, target, params}` | `Accessor.SendNotify` |
| action_change_terrain.go | change_terrain | `{position{x,y}, terrain_id}` | `Accessor.ChangeTerrain` |

示例（`action_apply_buff.go`）：

```go
// 本文件实现apply_buff规则动作：按配置参数给目标实体挂载Buff。
// 拆分为独立文件+init()注册，新增内置动作只需在rule包内新增同类文件。

package rule

import "fmt"

// applyBuffHandler apply_buff动作处理器，薄处理器，副作用经ActionAccessor端口调用服务实现。
type applyBuffHandler struct{}

// Type 返回动作类型标识"apply_buff"。
func (h *applyBuffHandler) Type() string { return "apply_buff" }

// Execute 解析参数并调用上下文访问器给目标挂载Buff，参数缺失返回错误。
func (h *applyBuffHandler) Execute(ctx ActionContext) error {
	buffID, _ := ctx.Params["buff_id"].(string)
	target, _ := ctx.Params["target"].(string)
	if buffID == "" || target == "" {
		return fmt.Errorf("动作apply_buff参数缺失，需要buff_id与target")
	}
	return ctx.Accessor.ApplyBuff(ctx, target, buffID)
}

// init 在rule包加载时向全局注册表注册apply_buff动作。
func init() { RegisterAction(&applyBuffHandler{}) }
```

### 3.6 题材层扩展方式（框架零改动）

// Execute 释放信息素，调用题材侧领域服务（经ActionAccessor或直接服务调用）。
func (h *pheromoneHandler) Execute(ctx rule.ActionContext) error {

// init 包加载时注册题材动作，服务入口blank import本包即可生效。

```go

)
```

### 3.7 启动全量校验

配置加载完成后、服务启动前：

1. 从 `rules.json`（rule_definitions）与 `rule_actions` 收集全部 `action_type`（去重）；
2. 调用 `ValidateTypes(configuredTypes)`；
3. 缺失类型非空 → 返回错误，**拒绝启动**，输出缺失动作类型清单与配置位置（文件 + 规则ID）。

**时序保证**：blank import 的包 `init()` 在 `main` 执行前由 Go 工具链保证完成，校验在 `main` 内启动流程调用，天然满足"先注册、后校验"。

### 3.8 与现有 rule.go RuleRegistry 的关系

**并列 + 组合，职责清晰划分：**

| 维度 | RuleRegistry（rule.go，现状） | ActionRegistry（action_registry.go，新增） |
|------|------------------------------|---------------------------------------------|
| 注册对象 | 扩展点ID → RuleExecutor（一条规则的完整执行器） | 动作类型 → RuleActionHandler（规则内的单个动作） |
| 粒度 | 规则级 | 动作级 |
| 注册时机 | 各服务启动时显式注册（`NewRuleRegistry`） | 内置 `init()` + 题材 `init()` 注册（blank import），包级全局 |
| 使用方 | 业务代码按扩展点ID执行整条规则 | 规则引擎内部按 action_type 分发单个动作 |

**组合关系**：规则引擎的 RuleExecutor 实现解析 rule 的 actions 列表，对每条 action 从 `GlobalActionRegistry().Get(action_type)` 取 handler，构造 ActionContext 执行。即 **RuleRegistry 管"这条规则由谁执行"，ActionRegistry 管"规则内这个动作由谁执行"**。

### 3.9 落地拆解（E2 的 3 个 Story 建议）

| Story | 内容 | 验收 |
|-------|------|------|
| E2-S1 | `action_registry.go`：RuleActionHandler + ActionContext + ActionAccessor + ActionRegistry + RegisterAction + ValidateTypes | 单测覆盖注册/重复/空/nil/查询/全量校验 |
| E2-S2 | 7 内置动作拆分 7 文件 `init()` 注册 + 端口签名 | 启动后 7 个动作全部可 Get 且可 Execute（mock Accessor）；参数缺失报错不 panic |
| E2-S3 | 启动全量校验接入 + 示例题材动作 blank import 验证 | 配置引用未注册动作拒绝启动；blank import 后题材动作可用，框架代码零 diff |

## 四、备选方案对比

| 方案 | 说明 | 评估 | 结论 |
|------|------|------|------|
| A. 写死枚举 + switch（现状） | 动作类型硬编码，新增动作改框架 | 违反骨肉分离；题材每次新增动作都要改框架代码并重新发版框架 | 否决 |
| B. 进程外插件（go-plugin 等） | 插件隔离、热插拔 | 跨进程序列化开销、部署/调试复杂；与微服务架构重复；P1/P2 无进程级热插拔需求，违反 YAGNI（规范4.5） | 否决 |
| C. 仅配置化（无 Go handler） | 动作参数全配置化 | 复杂动作（触发战斗/生成实体/条件分支）无法纯配置表达，最终仍需代码；"配置中放代码逻辑"违反规范4.4 | 否决 |
| D. 注册表 + init() 注册（选定） | 见第三章 | Go 原生模式，编译期类型安全，零第三方依赖；题材层 blank import 即扩展；与现有 RuleRegistry 风格一致（复用其错误处理范式） | ✅ 选定 |

## 五、影响范围

| 范围 | 影响 |
|------|------|
| 规则系统执行器 | 规则执行器从 `switch(action_type)` 改为"查 ActionRegistry 分发"；未注册动作类型返回错误并记录日志（结构化日志由宿主服务 zap 记录，共享内核不引入日志依赖） |

| 文档 | 设计书 3.8.2 动作类型契约从"不可配置"修订为"注册表可扩展"，以本 ADR 为权威规格 |

## 六、验收标准（对齐开发计划 E2）

- [ ] **启动全量校验**：`rules.json`/`rule_actions` 引用未注册的 `action_type` 时服务拒绝启动，错误信息含缺失类型与配置位置；
- [ ] **7 动作独立 init 注册**：apply_buff 等 7 个动作各自独立文件 `init()` 注册，注册表启动后 7 个动作全部可 Get 且可 Execute（mock Accessor）；
- [ ] **重复注册报错**：同一动作类型重复注册返回错误（`Register` 返回 error，`RegisterAction` panic）；
- [ ] **blank import 扩展**：题材层示例动作（如 `release_pheromone`）注册成功，框架代码零 diff（git diff 仅新增题材包文件）；
- [ ] 动作参数缺失时返回错误并跳过（不 panic、不静默）；
- [ ] 单测覆盖率：注册表/7 内置动作 ≥ 80%（application/domain 层要求）；
- [ ] 文档同步：设计书 3.8.2 与 03-规则系统.md 动作类型契约口径统一（E7 契约对齐时复核）。
