## 一、背景与问题

### 1.1 现状

| 事实 | 位置 | 说明 |
|------|------|------|
| 业务切换边界已定义 | spec.md 规则9 | 进行中战斗用**开战时配置快照**；进行中移动/生产下个 Tick 用**当前最新配置**；联盟外交用最新配置 |
| 战斗快照语义分裂 | spec.md 功能9/10 | 开战前拉取参战方属性快照冻结；**长时战斗（>30秒）每轮刷新关键属性快照**（从 Social 拉取），保证科技/赛季 Buff 变更后公平——这使"属性"与"公式/克制"分属两个版本域 |
| 现有战斗聚合根无版本字段 | `server/combat/domain/combat/aggregate.go` | `Combat` 只有 combatID/combatType/status/currentRound/maxRounds/attackerIDs/defenderIDs/formationID/startTime，**无 config_version、无属性快照结构、无种子字段** |
| 配置查询无版本化 API | `server/shared/pkg/config/query_api.go` | ConfigQueryAPI 只支持查询"当前版本"配置，无 `GetWithVersion`；配置热更原子替换后，旧版本配置从内存被替换，无版本保留机制 |
| 热更无发布前实例扫描 | `server/shared/pkg/config/hot_reload.go` | `HandleReload` 流程 = 编译校验 → 原子替换 → 触发业务回调 → 更新版本号；**无"删除配置项被进行中实例引用"的检查** |
| 种子派生已定但未绑定快照 | ADR-001 3.3 / `server/shared/pkg/formula/random.go` | 战斗种子 = `hash(combatID, config_version, round)`；若 config_version 取"当前版本"而非"快照冻结值"，热更/回滚会漂移重放种子 |

### 1.2 三方冲突的具体场景（评审高风险#2）

**场景A：热更删除兵种 → 隐性引用断裂**

```
T0  战斗开始，快照 config_version=N，编队含兵种"螳螂"（units.json#mantis），克制矩阵含 mantis 行
T1  运营热更删除"螳螂"，config_version=N+1（配置包兼容性校验通过——因为存量玩家兵种可能已迁移或校验漏过进行中实例）
T2  Social 收到 player.attribute_changed，按新配置回写属性（mantis 已删 → 属性归零或走默认值）
T3  Combat 轮次执行：公式/克制矩阵仍按"当前版本"查询 → mantis 条目已删 → 查询返回零值/错误
T4  结算：combat_loot_rules 引用已删兵种/资源类型 → 战利品错发、战报错误或 panic
```

**场景B：回滚撕裂已应用状态**

```
T0  热更 N→N+1 成功，10 秒内战斗 B1、生产队列 P1 已按 N+1 开始
T1  运营发现 N+1 有误，RollbackConfig 回滚到 N
T2  进行中 B1/P1 的版本归属未定义：继续用 N+1 还是回退 N？回退后 N+1 配置是否立即清理？
T3  若 N+1 被清理而 B1 仍引用 → 版本化查询失败 → 与场景A同构的断裂
```

**场景C：重放种子漂移**

```
T0  战斗 B1 第 3 轮开始，config_version=N（当前）
T1  轮次执行中途热更 N→N+1
T2  第 4 轮若种子派生取"当前版本 N+1" → 与战报记录的第 3 轮种子（基于 N）不一致
T3  重放（对账/战报/审计）时无法还原真实结果 → 战斗回放一致性被破坏
```

**冲突本质**：战斗的**配置引用域**（公式/克制/技能/战利品/战斗类型）与**实体属性域**（每轮从 Social 刷新）跨越了两个版本；热更/回滚改变配置版本时，这两个域失去同一基准，形成隐性引用断裂。现有"配置包兼容性校验"只覆盖**存量数据**（玩家资源/地形/兵种），**不覆盖进行中的战斗/行军/生产实例**；回滚只定义"校验失败回滚"，未定义"已应用后回滚"的版本归属。

### 1.3 评审结论

《通用SLG框架设计评审报告》高风险#2 原文修复建议（三条，本 ADR 全部落地）：

1. 战斗快照绑定 `config_version`，结算时校验快照配置仍存在，缺失则走熔断协议（用兜底配置结算或强制平局）；
2. 回滚定义双向切换语义：新配置→旧配置时，进行中业务如何归属（继续用新/回退旧）；
3. 热更删除配置项时，必须扫描进行中实例引用（战斗、行军、生产队列），阻塞或降级。

《通用SLG服务端开发计划》将其列为 **P1-E3**，验收关键点："注册→建→产兵→行军→战斗→结算→背包跑通；**热更删配置走熔断**"；风险#2 缓解动作："config_version + 熔断 + 实例扫描（E3先落地）"。

## 二、决策

**采用：战斗快照绑定 config_version + 版本化配置查询 + 结算校验熔断协议 + 热更删除实例扫描 + 双向回滚语义。**

五个组成部分：

1. **快照绑定版本**：`CombatSnapshot` 携带 `ConfigVersion`（开战时配置版本），战斗期**全部配置引用**（公式/克制矩阵/技能/战利品规则/战斗类型/阶段）通过**版本化查询** `ConfigQueryAPI.GetWithVersion(extPointID, key, configVersion)` 读取，与当前版本解耦；
2. **结算校验 + 熔断协议**：结算前校验快照引用的配置项在快照版本仍存在，缺失 → 按熔断策略处理（默认强制平局，可选兜底配置结算），发布 `combat.circuit_broken` 事件；
3. **热更删除实例扫描**：Config Service 发布前执行两阶段预检（扫描进行中战斗/行军/生产队列对**待删除配置项**的引用），有引用 → 阻塞（abort）并输出冲突清单；运营强制发布 → 相关实例标记"待熔断"；
4. **双向回滚语义**：快照类业务（战斗/生产队列）保持开始版本不因回滚改变，即时类业务（移动/外交）跟随当前版本；**版本保留受引用计数保护**——只要存在进行中实例引用某版本，该版本配置不清理；
5. **种子派生绑定快照**：战斗种子取**快照冻结的 config_version**（非当前版本），热更/回滚不漂移，重放一致性由快照冻结保证。

## 三、设计要点

### 3.1 CombatSnapshot 绑定 ConfigVersion

**快照自包含原则**：战斗一经开始，其配置引用域被冻结到开战版本——快照不仅记录参战方属性，还记录"本场战斗以哪个配置版本为基准"。所有战斗期配置读取不再走"当前版本"查询，一律走 `GetWithVersion(snapshot.configVersion)`。

```go
// CombatSnapshot 战斗快照，冻结开战时参战方属性与配置版本。
// 配置引用域（公式/克制/技能/战利品/战斗类型）以 configVersion 为唯一基准，
// 战斗期配置查询一律走版本化查询，与当前热更版本解耦（ADR-004 3.1）。
type CombatSnapshot struct {
	configVersion int64               // 开战时配置版本号，战斗全程引用该版本，不因热更/回滚改变
	combatType    int                 // 战斗类型（1=野战 2=攻城 3=城战），开战时冻结，对应快照版本 combat.json
	formulaID     string              // 本场伤害公式ID，开战时冻结，对应快照版本 formulas.json
	attackerProps map[int64]PropEntry // 攻击方实体属性快照，key=实体ID；长时战斗按 spec.md 功能10 每轮刷新
	defenderProps map[int64]PropEntry // 防守方实体属性快照，key=实体ID
	skillIDs      []string            // 本场启用技能ID列表，开战时冻结，对应快照版本 combat_skills
	lootRuleID    string              // 战利品规则ID，开战时冻结，对应快照版本 combat_loot_rules
}

// PropEntry 参战方单实体属性快照项。
type PropEntry struct {
	entityID int64             // 实体ID，对应World中的实体
	atk      int64             // 攻击力（int64，AGENTS.md规范8）
	def      int64             // 防御力
	hp       int64             // 当前血量
	unitType int               // 兵种类型ID，对应快照版本 units.json；删除该兵种即触发结算熔断
	tags     map[string]struct{} // 实体标签（克制矩阵查询用），开战时冻结
}
```

**版本化配置查询**（config 共享内核新增能力）：

```go
// ConfigQueryAPI 版本化配置查询接口（在 query_api.go 现有接口上扩展）。
// 新增 GetWithVersion：进行中快照类业务以冻结版本读取配置，不随热更漂移。
type ConfigQueryAPI interface {
	// GetWithVersion 按指定配置版本查询配置项；版本缺失或配置项缺失返回错误。
	GetWithVersion(ctx context.Context, extPointID string, key string, configVersion int64) (any, error)
	// HasWithVersion 判断指定配置版本中是否存在某配置项，供结算校验使用。
	HasWithVersion(ctx context.Context, extPointID string, key string, configVersion int64) (bool, error)
	// PinVersion 锁定配置版本，增加引用计数；进行中快照类业务创建时调用。
	PinVersion(ctx context.Context, configVersion int64) error
	// UnpinVersion 释放配置版本引用计数，归零且超出保留上限后允许清理。
	UnpinVersion(ctx context.Context, configVersion int64) error
}
```

**版本保留机制**：config 模块为每个版本维护引用计数。`PinVersion` 在快照类业务创建时 +1，`UnpinVersion` 在业务结束时 -1。版本清理条件 = 引用计数为 0 **且** 超出 `max_config_version_history`（默认 10）。即：**进行中实例引用的版本永不因历史滚动被清理**（解决场景B/回滚后的版本保留问题）。

### 3.2 结算校验流程与熔断协议

**结算流程（settle 阶段入口）**：

```
结算开始
   ↓
ValidateSnapshotConfig(snapshot, configQuery)
   ↓ 有缺失配置项？
   ├─ 否 → 正常结算（按快照版本公式/战利品规则）
   └─ 是 → 熔断决策（CircuitBreakPolicy）
             ├─ 策略=FallbackSettle → 用兜底配置结算，战报标注"熔断-兜底"
             └─ 策略=ForceDraw（默认）→ 强制平局，不发放战利品，不产生赛季积分
   ↓
发布 combat.ended / combat.circuit_broken 事件
```

**熔断策略选择规则**（按缺失配置项类型分派，运营可配置）：

| 缺失项类型 | 默认策略 | 理由 |
|-----------|---------|------|
| 实体定义类（兵种/技能/阵型/战利品规则） | **ForceDraw 强制平局** | 缺失实体定义 = 战斗参与方身份不成立，无法可靠计算任何一方的战利品；兜底结算可能错发资源、双花，破坏经济 |
| 数值类（伤害公式/克制倍率/地形修正） | **FallbackSettle 兜底配置结算**（需运营在 combat.json 预置兜底公式） | 数值缺失不影响"谁胜谁负"的身份判定，用兜底公式结算可保留战果；未预置兜底公式时回落 ForceDraw |

> 决策依据：**经济安全性优先于战斗结果完整性**。SLG 中战利品/赛季积分是权威方交接的经济来源，宁可平局损失一场战斗体验，不可错发资源造成对账失败（spec.md 4.2 资源操作准确率 99.999%）。FallbackSettle 是运营显式选择承担经济风险的通道，必须预置兜底公式才允许。

**熔断事件**：`combat.circuit_broken` 事件携带 combatID / 缺失项清单 / 采用策略 / 最终结果，供运营告警与 E4 验证报告统计。熔断次数计入可观测性指标 `combat_circuit_break_total`。

### 3.3 热更删除配置项的实例扫描

**两阶段预检（prepare → commit/abort）**：Config Service 在**写 etcd 之前**执行预检，各业务服务实现 `ConfigDependencyScanner` 报告进行中实例对待删除配置项的引用。

**变更类型分派**：

| 热更变更类型 | 判定 | 处理 |
|------------|------|------|
| 新增 | 新配置项 ID 不在旧版本 | 直接放行（无引用断裂风险） |
| 修改 | ID 存在、值变化 | **降级放行**：进行中快照类业务走版本化查询（继续用旧版本），即时类业务下个 Tick 用新值，无需扫描 |
| 删除 | 旧配置项 ID 在新版本缺失 | **扫描**：有进行中实例引用 → 阻塞（abort）；运营强制发布 → 实例标记"待熔断" |

**扫描接口**（各业务服务实现，归属 domain 层声明、infrastructure 层实现）：

```go
// ConfigDependencyScanner 进行中实例配置引用扫描接口，热更删除类变更前调用。
// 各业务服务实现，Config Service 发布预检时通过 gRPC 汇聚结果（spec.md 缺口11 跨服务一致性）。
type ConfigDependencyScanner interface {
	// ScanCombatRefs 扫描进行中战斗对指定配置项ID的引用（公式/克制/技能/战利品/兵种）。
	ScanCombatRefs(ctx context.Context, deletedIDs []string) ([]InstanceRef, error)
	// ScanMovementRefs 扫描进行中行军对指定配置项ID的引用（移动类型/消耗表/地形）。
	ScanMovementRefs(ctx context.Context, deletedIDs []string) ([]InstanceRef, error)
	// ScanProductionRefs 扫描进行中生产/采集队列对指定配置项ID的引用（产出公式/资源类型）。
	ScanProductionRefs(ctx context.Context, deletedIDs []string) ([]InstanceRef, error)
}

// InstanceRef 进行中实例引用记录，热更预检冲突清单条目。
type InstanceRef struct {
	instanceType int    // 实例类型：1=战斗 2=行军 3=生产队列
	instanceID   int64  // 实例ID（战斗ID/移动订单ID/生产队列ID）
	refExtPoint  string // 被引用扩展点ID，如"combat.damage_formulas"
	refKey       string // 被引用配置项ID，如被删除的兵种ID
	configVersion int64 // 实例开始时的配置版本号
}
```

**阻塞与降级语义**：

- **阻塞（abort）**：预检发现引用 → Config Service 拒绝发布删除类热更，返回冲突清单（实例ID + 引用项 + 开始版本）给运营后台，运营决定处理（等待实例结束 / 强制发布 / 放弃删除）；
- **强制发布（force）**：运营显式强制 → 热更继续，但冲突实例**标记"待熔断"**（快照记录 `circuitPending=true`），结算/产出时走 3.2 熔断协议，不静默错发；
- **降级（modify 类）**：无需扫描，版本化查询天然隔离——进行中实例继续用冻结版本，不受影响。

**与现有热更链路衔接**：`ConfigHotReloader.HandleReload` 入口前插入预检阶段（或由 Config Service 在 application 层编排：预检 → 通过后写 etcd → 各服务 watch 生效）。预检超时按 `config_validation_timeout_seconds`（默认 10 秒）处理，超时按"存在引用"保守处理（阻塞），避免漏扫。

### 3.4 双向回滚语义

**回滚 = 从新版本 N 回退到旧版本 N-1（运营 RollbackConfig）**。回滚的版本归属按业务类型分三类：

| 业务类型 | 版本归属规则 | 理由 |
|---------|-------------|------|
| 快照类（战斗/生产队列） | **保持开始版本**：进行中战斗继续用 N 快照（版本化查询），已开始的产出队列继续用 N；**不因回滚追溯改变** | 快照语义承诺"开战时锁定"，回滚改变会破坏战斗公平性与回放一致性 |
| 即时类（移动/外交/属性回写） | **跟随当前版本**：回滚后下个 Tick/下次查询自然用 N-1 | spec.md 规则9 本就定义移动/外交用"当前最新配置"，回滚即版本切换 |
| 新建业务 | 用回滚后版本 N-1 | 无历史包袱 |

**关键配套：版本保留引用计数**。回滚后若 N 被标记可清理，但仍有进行中战斗引用 N → 引用计数 > 0，N **保留不清**（3.1 PinVersion/UnpinVersion）。待最后一场引用 N 的战斗结束后，N 才进入正常历史滚动清理。**禁止在存在引用时物理删除配置版本**——否则与场景B同构断裂。

**回滚的原子性**：回滚与热更同路径（`HandleReload`），同样执行编译校验 + 版本化切换；校验失败的回滚也回滚（保持 N）。回滚操作记审计日志（操作人/操作时间/从版本/到版本/受影响进行中实例数）。

### 3.5 与E1种子派生的衔接（重放一致性）

ADR-001 3.3 已定：战斗种子 = `hash(combatID, config_version, round)`。本 ADR 明确 **config_version 取快照冻结值**：

- 战斗创建时：`snapshot.configVersion = ConfigHotReloader.CurrentVersion()`，同时 `PinVersion`；
- 每轮种子：`DeriveRoundSeed(combatID, snapshot.configVersion, round)` —— config_version 在战斗期间**恒等于快照值**，热更/回滚不改变；
- 重放一致性方案：
  1. 战报记录：combatID + snapshot.configVersion + 每轮种子 + 每轮结果摘要（ADR-001 3.3"战报记录种子"）；
  2. 重放时：用战报中的 config_version 重建 `Pcg32`，逐轮重新求值，与真实结果逐轮比对；
  3. 因 config_version 冻结，**热更/回滚发生在战斗中途也不影响重放**——快照版本仍在（引用计数保护），重放按快照版本查询配置，随机序列一致；
  4. 校验工具（E3-S5）提供 `ReplayCombat(report)` 断言逐轮结果一致，E4 切片验证报告覆盖。

**设计张力说明**：有人会问"种子为何要含 config_version？直接只含 combatID+round 岂不更简单"。理由：config_version 参与种子是为了保证**跨版本重放可区分**——同 combatID 理论不可复用（雪花唯一），但同一战斗若因故障迁移/重新创建，config_version 确保不同配置版本下的随机流不串；且 ADR-001 已冻结此约定，本 ADR 只固定"取快照值"消除漂移，不改变种子构成（避免破坏已实现的 random.go）。

**快照与熔断（combat 领域，归属 `server/combat/domain/combat/`）**：

```go
// Package combat 战斗聚合根，维护战斗状态与轮次执行。
// 本文件实现战斗快照配置版本绑定与结算熔断协议（ADR-004）：
// 快照携带开战 config_version，结算前校验配置仍存，缺失走熔断策略。
package combat

import (
	"context"
	"fmt"
	"strconv"

	"insectworld/server/shared/pkg/config"
)

// 熔断策略常量（规范1：就近归属战斗领域）。
const (
	// CircuitBreakFallbackSettle 兜底配置结算：按 combat.json 预置的兜底公式结算，战报标注"熔断-兜底"。
	CircuitBreakFallbackSettle = 1
	// CircuitBreakForceDraw 强制平局：按平局结束，不发放战利品、不产生赛季积分（默认）。
	CircuitBreakForceDraw = 2
)

// CircuitBreakPolicy 熔断策略，由 combat.json 配置注入（config.circuit_breaker 扩展点）。
type CircuitBreakPolicy struct {
	strategy           int    // 熔断策略：1=兜底配置结算 2=强制平局（默认2）
	fallbackFormulaID  string // 兜底结算公式ID，strategy=1 时必须预置且存在于快照版本 formulas.json
	fallbackLootRuleID string // 兜底战利品规则ID，strategy=1 时使用；缺失时仅结算战斗结果不发放战利品
}

// ValidateSnapshotConfig 结算前校验快照引用的配置项在快照版本仍存在。
// 返回缺失配置项清单；空清单表示可正常结算。快照版本由引用计数保护，正常路径不应缺失，
// 缺失仅发生在运营强制发布删除类热更且未等待实例结束的场景（ADR-004 3.3 强制发布）。
func ValidateSnapshotConfig(ctx context.Context, s *CombatSnapshot, query config.ConfigQueryAPI) ([]MissingConfigRef, error) {
	if s == nil {
		return nil, fmt.Errorf("快照不能为空")
	}
	if query == nil {
		return nil, fmt.Errorf("配置查询接口不能为空")
	}
	var missing []MissingConfigRef
	// 战斗类型缺失：无法判定阶段流程，必须熔断
	exists, err := query.HasWithVersion(ctx, config.ExtPointCombatTypes, strconv.Itoa(s.combatType), s.configVersion)
	if err != nil {
		return nil, fmt.Errorf("校验战斗类型失败: %w", err)
	}
	if !exists {
		missing = append(missing, MissingConfigRef{ExtPointID: config.ExtPointCombatTypes, RefKey: strconv.Itoa(s.combatType)})
	}
	// 伤害公式缺失：无法计算伤害，必须熔断
	exists, err = query.HasWithVersion(ctx, config.ExtPointDamageFormulas, s.formulaID, s.configVersion)
	if err != nil {
		return nil, fmt.Errorf("校验伤害公式失败: %w", err)
	}
	if !exists {
		missing = append(missing, MissingConfigRef{ExtPointID: config.ExtPointDamageFormulas, RefKey: s.formulaID})
	}
	// 参战方兵种缺失：实体定义不成立，必须熔断
	// 注：config.ExtPointUnitTypes 对应 units.json 的实体类型扩展点（entity.entity_types），
	// 该常量当前尚未在 extension_registry.go 定义，E3-S1 实现时补充（与 07-配置加载.md 口径一致）。
	for entityID, prop := range s.attackerProps {
		exists, err = query.HasWithVersion(ctx, config.ExtPointUnitTypes, strconv.Itoa(prop.unitType), s.configVersion)
		if err != nil {
			return nil, fmt.Errorf("校验兵种失败: %w", err)
		}
		if !exists {
			missing = append(missing, MissingConfigRef{ExtPointID: config.ExtPointUnitTypes, RefKey: strconv.Itoa(prop.unitType), InstanceID: entityID})
		}
	}
	// 防御方兵种同构校验，代码略（E3-S2 实现时对称补齐）
	// 战利品规则缺失：影响经济，必须熔断（缺失时 ForceDraw 或兜底不发放战利品）
	exists, err = query.HasWithVersion(ctx, config.ExtPointCombatLootRules, s.lootRuleID, s.configVersion)
	if err != nil {
		return nil, fmt.Errorf("校验战利品规则失败: %w", err)
	}
	if !exists {
		missing = append(missing, MissingConfigRef{ExtPointID: config.ExtPointCombatLootRules, RefKey: s.lootRuleID})
	}
	return missing, nil
}

// MissingConfigRef 结算校验缺失配置项记录。
type MissingConfigRef struct {
	ExtPointID string // 扩展点ID，如"combat.damage_formulas"
	RefKey     string // 配置项ID，如被删除的兵种ID
	InstanceID int64  // 引用实例ID（实体ID），非实体引用时为0
}

// ResolveCircuitBreak 按熔断策略决策缺失配置的结算路径，返回最终战斗结果。
// 默认策略为强制平局（经济安全性优先）；兜底配置结算仅当策略显式配置且兜底项存在时使用。
func ResolveCircuitBreak(ctx context.Context, policy CircuitBreakPolicy, missing []MissingConfigRef, query config.ConfigQueryAPI, configVersion int64) (int, error) {
	// 无缺失 → 正常结算路径由调用方处理，本函数仅处理熔断决策
	if len(missing) == 0 {
		return 0, fmt.Errorf("无缺失配置项，无需熔断决策")
	}
	switch policy.strategy {
	case CircuitBreakFallbackSettle:
		// 兜底结算：校验兜底公式在快照版本存在，否则回落强制平局
		if policy.fallbackFormulaID == "" {
			return ResultDraw, nil // 未预置兜底公式 → 回落强制平局，保证经济安全
		}
		hasFormula, err := query.HasWithVersion(ctx, config.ExtPointDamageFormulas, policy.fallbackFormulaID, configVersion)
		if err != nil {
			return 0, fmt.Errorf("校验兜底公式失败: %w", err)
		}
		if !hasFormula {
			return ResultDraw, nil // 兜底公式在快照版本缺失 → 回落强制平局，保证经济安全
		}
		return ResultAttackerWin, nil // 兜底结算按快照版本执行（调用方按战报标注"熔断-兜底"）
	case CircuitBreakForceDraw:
		return ResultDraw, nil // 强制平局，不发放战利品
	default:
		return 0, fmt.Errorf("未知熔断策略: %d", policy.strategy)
	}
}
```

**种子派生（combat 领域，衔接 E1）**：

```go
// 种子派生函数需要 import "hash/fnv"（FNV-1a 哈希，确定性、跨Go版本稳定）与 "fmt"。

// DeriveRoundSeed 按快照冻结版本派生轮次随机种子（ADR-001 3.3 / ADR-004 3.5）。
// configVersion 必须取 CombatSnapshot.configVersion（开战冻结值），禁止取当前热更版本，
// 否则热更/回滚会使重放种子漂移，破坏战斗回放一致性。
func DeriveRoundSeed(combatID int64, configVersion int64, round int) uint64 {
	seed := fnv.New64a()
	seed.Write([]byte(fmt.Sprintf("%d:%d:%d", combatID, configVersion, round)))
	return seed.Sum64()
}
```

**热更预检（config 领域，归属 `server/config/domain/`）**：

```go
// Package configsvc 配置服务领域模型。
// 本文件实现热更发布前删除配置项实例扫描的两阶段预检（ADR-004 3.3）。
package configsvc

// 热更预检决策常量。
const (
	// ReloadAllow 预检通过，允许发布。
	ReloadAllow = 1
	// ReloadBlock 预检发现引用，阻塞发布（默认，保守安全）。
	ReloadBlock = 2
	// ReloadForce 运营强制发布，冲突实例标记待熔断。
	ReloadForce = 3
)

// ReloadPrecheckResult 热更发布预检结果，由各服务 Scanner 汇聚生成。
type ReloadPrecheckResult struct {
	decision    int            // 预检决策：1=允许 2=阻塞 3=强制
	conflicts   []InstanceRef  // 冲突引用清单（阻塞/强制时非空）
	deletedIDs  []string       // 本次删除的配置项ID
	forceBy     string         // 强制发布操作人（decision=3 时记录，审计用）
}

// PrecheckDeleteRefs 删除类热更发布前预检：汇聚各业务服务进行中实例对待删除配置项的引用。
// 有引用且未强制 → 返回阻塞；运营强制 → 返回强制并附冲突清单供标记待熔断。
// ctx 携带超时（config_validation_timeout_seconds），超时按存在引用保守阻塞。
// scanners 为各业务服务实现的 ConfigDependencyScanner（3.3 节定义，归属共享内核 configdeps 包，
// Config Service 与业务服务共用该接口类型），Config Service 通过 gRPC 汇聚结果
// （spec.md 缺口11 跨服务一致性），本函数为领域层决策纯逻辑。
func PrecheckDeleteRefs(ctx context.Context, scanners []configdeps.ConfigDependencyScanner, deletedIDs []string, force bool, operator string) (*ReloadPrecheckResult, error) {
	var conflicts []InstanceRef
	for _, sc := range scanners {
		combatRefs, err := sc.ScanCombatRefs(ctx, deletedIDs)
		if err != nil {
			return nil, fmt.Errorf("扫描战斗实例引用失败: %w", err)
		}
		conflicts = append(conflicts, combatRefs...)
		// 行军/生产队列同构汇聚，代码略（E3-S3 实现时对称补齐）
	}
	if len(conflicts) == 0 {
		return &ReloadPrecheckResult{decision: ReloadAllow, deletedIDs: deletedIDs}, nil
	}
	if force {
		return &ReloadPrecheckResult{decision: ReloadForce, conflicts: conflicts, deletedIDs: deletedIDs, forceBy: operator}, nil
	}
	return &ReloadPrecheckResult{decision: ReloadBlock, conflicts: conflicts, deletedIDs: deletedIDs}, nil
}
```

## 四、备选方案对比

| 方案 | 说明 | 评估 | 结论 |
|------|------|------|------|
| A. 不做校验（现状） | 快照不绑版本，战斗期配置查询当前版本 | 热更删兵种后战斗引用空配置：公式/克制返回零值、战利品错发或 panic，隐性引用断裂不可观测；回滚撕裂无解 | 否决 |
| B. 全量锁热更 | 热更期间暂停全部业务（战斗/移动/生产） | 违背 spec.md 规则11"热更不重置运行时状态"；热更生效需 <10 秒（spec.md 4.1）但锁全服不可接受；SLG 在线战斗频繁，删除类热更几乎永远等不到空窗 | 否决 |
| C. 战斗期间禁止热更 | 有进行中战斗即禁止删除类热更 | 长时战斗（>30秒）+ 高并发场景下删除类热更长期无法发布，运营不可接受；且只堵战斗不堵行军/生产队列 | 否决 |
| D. 快照绑定 + 版本化查询 + 结算校验熔断 + 实例扫描 + 双向回滚（**选定**） | 见第三章 | 快照绑定消除配置引用域漂移；版本化查询隔离热更影响；结算校验熔断兜底极端场景（不 panic、不误发）；实例扫描把风险前置到发布时；双向回滚语义补全"已应用后回滚"缺口；与 ADR-001 种子约定无缝衔接；实现量可控（E3 估算 10 人日含主链路） | ✅ 选定 |

## 六、验收标准（对齐开发计划 E3）

- [ ] **快照绑定**：`CombatSnapshot.ConfigVersion` 存在且等于开战时 `ConfigHotReloader.CurrentVersion()`；战斗期全部配置读取经 `GetWithVersion`，热更/回滚不改变进行中战斗的配置基准；
- [ ] **结算校验熔断**：热更删除兵种后，进行中战斗结算走熔断协议——默认强制平局、不发放战利品、不产生赛季积分、不 panic、不误发；兜底配置结算仅当策略显式配置且兜底项在快照版本存在；
- [ ] **实例扫描**：删除类热更发布前扫描进行中战斗/行军/生产队列，有引用 → 阻塞并输出冲突清单（实例ID+引用项+开始版本）；运营强制发布 → 实例标记"待熔断"；修改类热更无需扫描、版本化查询隔离；
- [ ] **双向回滚**：N→N-1 回滚后，进行中战斗继续用 N 快照结算正确；引用 N 的版本在最后引用结束前不被清理；回滚操作记审计日志；
- [ ] **重放一致性**：战斗中途发生热更/回滚，`ReplayCombat` 用战报记录的 config_version 重放，逐轮结果与真实一致（random 回放一致，对齐 ADR-001 验收）；
- [ ] **主链路切片**：注册→建→产兵→行军→战斗→结算→背包跑通（开发计划 E3 关键验收点）；
- [ ] 单测覆盖率：快照/校验/熔断/扫描/回滚/种子 ≥ 80%（application/domain 层要求），`go test -race` 通过；
- [ ] 知识缺口闭环：实现中发现本 ADR 与 etcd revision 重放/版本存储介质冲突时回写本 ADR 并触发评审（不静默改口径）。
