# 框架总览

## 1.1 什么是"引擎-配置分离"

### 核心图解

```
┌─────────────────────────────────────────────────────────────────┐
│                        SLG 游戏产品                              │
│                                                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                     内容配置层                       │   │
│  │  种族 · 兵种 · 建筑 · 英雄 · 技能 · 公式 · 克制矩阵      │   │
│  │  资源类型 · 地形 · 事件 · 赛季规则 · 联盟规则 · ……        │   │
│  └──────────────────────┬──────────────────────────────────┘   │
│                         │ 框架扩展接口（扩展点 + 契约）          │
│  ┌──────────────────────┴──────────────────────────────────┐   │
│  │                     引擎核心层                      │   │
│  │  实体 · 地图 · 移动 · 战斗 · 经济 · Buff · 规则          │   │
│  │  联盟 · 赛季 · 事件 · 网络同步 · 持久化                   │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 核心模块、内容配置、框架扩展接口的关系

| 概念 | 定义 | 技术对应 |
|------|------|---------|
| 核心模块 | 框架提供的通用机制，不包含任何具体游戏内容 | 引擎子系统 / 框架内置组件 |
| 内容配置 | 游戏配置挂载的具体内容，决定游戏的"皮相" | 配置文件 / 数据包 / Content Pack |
| 框架扩展接口 | 每个核心模块暴露的扩展点，内容配置必须按契约实现才能挂上去 | 接口契约 / Extension Point Contract |

### 引擎-配置分离的本质

- **核心模块不变**：换皮时，14根核心模块的代码零修改
- **内容配置可替换**：同一套核心模块，挂不同的内容配置=不同的SLG
- **接口稳定**：框架扩展接口是框架最核心的契约，变更需要全量回归验证

## 1.2 框架设计原则

| 原则 | 含义 | 反模式 | 验证方法 |
|------|------|--------|---------|
| **机制通用，内容可配** | 框架只实现机制，所有具体内容由配置注入 | 框架代码里出现"步兵""弓箭手"等具体名词 | 代码审查：框架源码中不出现任何游戏特定字符串 |
| **扩展点显式** | 每个可扩展的位置都有明确的ID和契约定义 | 通过hack或monkey-patch修改框架行为 | 扩展点注册表：所有扩展点有唯一ID和Schema定义 |
| **零硬编码** | 框架内不出现任何游戏特定的数值、公式、枚举值 | `if (unitType == "warrior") damage *= 1.5` | 静态扫描：框架代码中无数值常量、无游戏特定枚举 |
| **配置即玩法** | 策划通过修改配置文件就能创造新玩法，不需要程序介入 | 每个新玩法都需要程序写新代码 | 通用性验证：三题材仅靠配置差异即可实现 |
| **最小惊讶** | 框架的默认行为应该是最常见SLG的默认行为 | 框架默认行为是某种冷门SLG的特殊规则 | 默认值审查：所有默认值符合主流SLG惯例 |
