# 客户端契约

> 框架采用服务端权威架构。服务端是唯一真相源，所有游戏逻辑由服务端裁决。客户端负责渲染、输入转发和体验优化预测。

---

## 架构声明

### 服务端权威模型

| 原则 | 说明 |
|------|------|
| 服务端唯一真相 | 所有游戏状态以服务端数据为准，客户端数据是服务端数据的缓存 |
| 服务端裁决 | 战斗结果、资源变更、移动结果等核心逻辑由服务端计算，客户端不可自行决定 |
| 客户端请求 | 客户端操作以请求形式发送给服务端，服务端处理后返回结果 |
| 客户端预测 | 客户端可对低风险操作做本地预测提升体验，但最终以服务端结果为准 |
| 作弊防护 | 客户端不可信，服务端对所有客户端请求做校验 |

### 为什么选择服务端权威

| 如果客户端权威 | 问题 |
|---------------|------|
| 客户端自己算伤害 | 玩家可修改内存篡改伤害值 |
| 客户端自己算资源 | 玩家可跳过消耗直接获得资源 |
| 客户端自己判移动 | 玩家可瞬移到任意位置 |
| 客户端自己判战斗 | 玩家可伪造胜利结果 |

SLG是多人对抗游戏，任何让客户端做核心裁决的设计都会导致作弊。服务端权威是多人游戏的标准架构。

---

## 职责边界

### 服务端职责

- 14根核心模块的全部逻辑执行
- 游戏状态的唯一持有者
- 所有操作结果的裁决
- 数据持久化
- 配置加载和校验
- 作弊检测和处理

### 客户端职责

| 职责 | 说明 | 可否本地决策 | 原因 |
|------|------|-------------|------|
| 渲染 | 将服务端状态渲染为画面 | 是 | 纯展示，不影响游戏逻辑 |
| 输入采集 | 采集玩家操作，封装为请求 | 是 | 仅采集不执行 |
| 状态缓存 | 缓存服务端同步的状态数据 | 否 | 只读缓存，不可修改 |
| 移动预览 | 玩家选择目的地时预览路径和消耗 | 是 | 仅预览不执行，服务端可能有不同路径 |
| UI状态 | 界面选中、展开、切换等 | 是 | 纯UI，不影响游戏状态 |
| 插值/平滑 | 对位置变更做插值动画 | 是 | 仅视觉表现，不改变逻辑位置 |
| 乐观执行 | 对已发送请求做本地预判 | 有限 | 仅限低风险操作，见预测规则 |

## 交互模式

### 标准请求-响应流程

```
客户端                              服务端
  │                                  │
  │  1. 玩家操作（点击移动）            │
  │  2. 封装请求（move_request）       │
  │  3. 本地预测（显示预览路径）        │
  │  4. 发送请求 ──────────────────→ │
  │                                  │  5. 校验请求（权限/参数/频率）
  │                                  │  6. 执行逻辑（移动系统）
  │                                  │  7. 生成结果
  │                                  │  8. 发布事件
  │  9. 接收响应 ←────────────────── │
  │ 10. 对比预测与结果                 │
  │ 11. 修正差异或确认预测             │
  │ 12. 更新渲染                       │
  │                                  │
```

### 服务端主动推送流程

```
客户端                              服务端
  │                                  │
  │                                  │  1. 游戏逻辑触发状态变更
  │                                  │  2. 判断需要同步的客户端
  │                                  │  3. 生成增量数据
  │  4. 接收推送 ←────────────────── │
  │  5. 更新本地缓存                   │
  │  6. 更新渲染                       │
  │                                  │
```

推送场景：其他玩家的操作结果、赛季阶段切换、游戏事件触发、配置热更通知。

### 断线重连流程

```
客户端                              服务端
  │                                  │
  │  1. 检测断线                      │
  │  2. 显示"重连中"                  │
  │  3. 重连请求 ──────────────────→ │
  │                                  │  4. 验证身份
  │                                  │  5. 检查宽限期内（默认300秒）
  │                                  │  6. 生成状态快照+增量补丁
  │  7. 接收全量快照 ←────────────── │
  │  8. 重建本地状态                   │
  │  9. 接收增量补丁 ←────────────── │
  │ 10. 应用补丁                       │
  │ 11. 恢复游戏                       │
  │                                  │
```

宽限期内：玩家状态在服务端保留，重连后恢复。宽限期超时：按 `reconnection_rules.on_timeout` 策略处理（kick/ai_takeover/freeze）。

## 客户端技术栈约定

| 层面 | 选型 | 说明 |
|------|------|------|
| 引擎 | Unity | 客户端渲染和交互 |
| 通信 | WebSocket | 长连接，服务端可主动推送 |
| 序列化 | Protobuf | 请求/响应/推送消息格式 |
| 状态管理 | 事件驱动 | 服务端推送→更新缓存→触发渲染 |
| 预测 | 乐观执行+回滚 | 低风险操作本地预判，服务端确认或修正 |

客户端不直接读取服务端内存，所有数据通过 WebSocket 同步。客户端不直接调用服务端函数，所有操作通过 Protobuf 消息请求。
