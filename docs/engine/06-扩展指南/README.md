# 框架扩展指南

> 框架设计为可扩展的。当现有核心模块和扩展点无法满足需求时，可以通过扩展配置、扩展接口、新增核心模块三种方式扩展。

---

## 6.1 扩展场景分类

| 扩展类型 | 影响程度 | 频率 | 风险 | 示例 |
|---------|---------|------|------|------|
| **扩展配置** | 🟢 低 | 高（日常） | 低 | 新增种族、新增兵种、新增资源 |
| **扩展接口** | 🟡 中 | 中（每季度） | 中 | 新增传送动作、新增攻城阶段 |
| **新增核心模块** | 🔴 高 | 低（每年） | 高 | 聊天系统、排行榜系统 |

**扩展原则**：

- 优先扩展配置，其次扩展接口，最后新增核心模块
- 扩展配置不影响框架代码，零风险
- 扩展接口需要修改核心模块代码，但影响范围可控
- 新增核心模块需要修改框架核心，需要全量回归验证

## 6.5 扩展决策树

```
需要新增功能？
  │
  ├─→ 现有核心模块+扩展点能否通过配置实现？
  │     │
  │     ├─→ 是 → 🟢 扩展配置（修改配置文件）
  │     │         风险：低
  │     │         步骤：修改配置→校验→测试
  │     │
  │     └─→ 否 → 现有核心模块能否通过新增扩展点实现？
  │               │
  │               ├─→ 是 → 🟡 扩展接口
  │               │         风险：中
  │               │         步骤：定义契约→实现代码→更新文档→回归测试
  │               │
  │               └─→ 否 → 🔴 新增核心模块
  │                         风险：高
  │                         步骤：定义核心模块→定义扩展点→实现代码→集成测试→全量回归
  │
  └─→ 不确定 → 先尝试扩展配置，如果不行再升级
```

**决策检查清单**：

1. ✅ 是否检查了所有现有扩展点？
2. ✅ 是否考虑了规则系统+事件系统的组合方案？（很多看似需要新扩展点的需求，可以通过规则+事件组合实现）
3. ✅ 扩展接口时，是否评估了对其他核心模块的影响？
4. ✅ 新增核心模块时，是否更新了依赖图和事件总线？
5. ✅ 是否运行了全量回归测试？

## 6.6 扩展时的注意事项

### 向后兼容

- 新增扩展点时，必须提供默认值，确保旧配置文件无需修改即可运行
- 新增核心模块时，必须确保旧配置文件不包含新核心模块的配置时框架仍可运行
- 持久化的迁移脚本必须覆盖新增字段

### 配置校验

- 每次新增扩展点后，必须更新配置校验器的校验规则
- 配置校验器应支持"严格模式"（报告所有问题）和"宽松模式"（只报告致命问题）
- 校验报告应包含：错误级别（致命/警告/建议）、错误位置、修复建议

### 事件扩展

- 新增事件类型时，必须在事件总线中注册，不可绕过事件总线直接调用
- 新增事件类型时，应检查是否与现有事件类型冲突
- 事件数据Schema一旦发布不可修改（只能新增字段，不可删除或修改已有字段）

### 性能影响

- 扩展配置：几乎无性能影响（只是配置数据）
- 扩展接口：需要评估扩展点调用频率和对主循环的影响
- 新增核心模块：需要评估新核心模块对整体性能的影响，特别是L5层核心模块（网络同步、持久化）

### 文档更新

- 每次扩展后必须更新本文档
- 更新内容：新扩展点契约、新核心模块定义、依赖图、事件类型表
- 文档版本号遵循语义化版本：扩展配置=patch，扩展接口=minor，新增核心模块=major
