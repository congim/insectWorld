## 一、核查方法与口径（为什么 05 验证的 100% 需要修正）

05-通用性验证的四步法把玩法特征**映射到"扩展点名"**（如"移动系统 movement_path_modifiers"），凡映射成功即计 100% 覆盖。这是**文档映射级**核查——它验证的是"扩展点存在"，**没有验证"扩展点契约的字段/语义能否承载该特征所需的全部能力"**。

本表升级为**契约表达力级**核查，对每个特征追问三件事：

1. **扩展点契约是否真实存在且字段齐备**（对照 07 配置总清单 Schema + 设计书第三章挂载点契约）；
2. **所需行为是否在"内置 7 动作 + 注册表"可承载范围内**（对照 ADR-003 统一后的动作枚举）；
3. **所需计算/条件是否在公式引擎函数库可表达范围内**（对照 ADR-001 冻结函数库）。

判定档位：

| 档位 | 含义 |
|------|------|
| ✅ 够用 | 现有扩展点 + 内置动作/注册表可直接表达，无需任何代码扩展 |
| ⚠️ 勉强-需组合 | 现有能力可组合表达主体；存在 1 处以上缺口（缺扩展点字段 / 缺动作 / 缺机制骨头），缺口需走扩展开发 |
| ❌ 缺 | 无契约承载，必须扩展开发 |

修复归属四类（与终版方案 A/B/C 对齐）：

| 修复归属 | 对应分层 | 说明 |
|---------|---------|------|
| 配置可表达 | B类（L2 配置文件） | 纯配置+规则组合即可，验证"配置化承诺"成立 |
| 需新骨头 | A类（L1 framework/mechanism） | 通用机制缺失（计划内 P3 六骨头），非题材专属 |
| 需新扩展点 | C类（L3 extensions 或 L1 扩展点） | 契约字段/语义缺口，需新增扩展点（题材专属或通用） |
| 需新动作handler | C类（L3 extensions，注册表承载） | 行为缺口，题材层实现 RuleActionHandler + init() 注册，框架零改动 |

### 2.2 规则动作枚举（ADR-003 统一后权威口径）

- **内置 7 个**：`apply_buff / remove_buff / modify_resource / spawn_entity / trigger_combat / send_notify / change_terrain`
- **custom**：题材层注册的动作类型标识（非内置，走注册表）
- **execute_formula**：内置动作候选，本期未内置（YAGNI，E14 再评估）
- 权威校验：ActionRegistry 启动全量校验，未注册动作拒绝启动

### 2.3 公式引擎函数库（ADR-001 冻结）

9 个内置函数 `min / max / floor / ceil / round / random(3签名) / clamp / abs / if` + 比较运算符（`> >= < <= == !=`）+ 逻辑运算符（`and / or / not`）= **12 项可调用能力（任务口径"12函数"）**；E4 已用 8 条真实昆虫公式验证（含条件分支 #6、随机 #1、函数嵌套 #7/#8），全部可编译可求值，同种子同结果。

### 2.4 分层与 A/B/C/D 分类（终版方案）

- **A类**：通用框架 21 根骨头（12 老 + 9 新），L1 framework/mechanism
- **B类**：配置化 18 文件，L2
- **C类**：扩展开发题材专属——终版原文列：**昆虫信息素路径/进化树/蛰伏、星际跃迁/三层战斗/虫洞、三国计策/附庸进贡、PVE副本形态、聊天**
- **D类**：后置（邮件）

### 4.3 配置化承诺的真实覆盖率

| 口径 | 覆盖率 | 说明 |

## 五、重点核查

### 5.1 核查一：ADR-001 公式引擎函数库（12 能力）能否覆盖三题材条件公式？

**结论：✅ 全覆盖，无公式缺口。**

| 题材 | 代表性公式 | 所需能力形态 | 函数库支撑 | 判定 |
|------|-----------|-------------|-----------|------|
| 昆虫 | 蛰伏产出 `if(season_phase=='winter', 产出×0.1, 产出)` | 条件分支+比较 | `if` + `==`（E4 验证集 #6 同型，已验证） | ✅ |
| 昆虫 | 进化成本 `基础成本 × (1 + 等级 × 0.5)` | 嵌套算术 | 四则+变量（E4 验证集 #4） | ✅ |
| 昆虫 | 伤害波动 `攻击 × (1-防御/100) × 克制 × random(0.9,1.1)` | 算术+随机 | `random(a,b)` 种子化（E4 验证集 #1，同种子同结果） | ✅ |
| 三国 | 兵种克制伤害 `max(atk × counter - def × terrain_mod, 1)` | 函数钳制+克制变量 | `max`（E4 验证集 #8） | ✅ |
| 三国 | 策反判定 `if(loyalty < 阈值 and 外交==敌对, 叛变, 保持)` | 逻辑组合 | `if` + `and` + 比较 | ✅ |
| 三国 | 攻城加成 `if(攻城器, 伤害×0.5, 伤害)` | 条件分支 | `if` | ✅ |
| 星际 | 层间拦截 `if(太空战失败, 0, 可进轨道战)` | 条件分支 | `if` + 逻辑 | ✅ |
| 星际 | 稀有资源科技解锁 `resource_gt(暗物质, 阈值)` | 比较+资源变量 | `>` + 资源变量（条件表达式与公式共享语法子集，ADR-001 3.5） | ✅ |
| 星际 | 跃迁消耗 `基础消耗 × (1 + 距离系数)` | 算术 | 四则 | ✅ |

**依据**：E4 实测 8 条真实公式已覆盖评审指出的全部缺口形态（条件分支 #6、随机 #1、函数调用 #7/#8、嵌套 #2/#3），三题材公式均可归入上述形态；ADR-001"知识缺口标记"未触发降级评审。三题材无超出函数库的表达需求。

### 5.2 核查二：ADR-002 注册表能否承载需要新动作的特征？

**结论：✅ 注册表足以承载全部 C 类动作缺口，框架零改动。**

| 需要新动作的特征 | 缺口动作 | 承载方式 | 判定 |
|-----------------|---------|---------|------|
| K2 信息素路径 | `release_pheromone` | 题材层实现 RuleActionHandler + init() 注册 + blank import；**ADR-002 3.6 官方示例正是此动作**，E16 验收项 | ✅ 注册表已就绪 |
| S2 武将策反 | `change_owner`（归属转移） | 题材层 handler，经 ActionAccessor 端口扩展或题材服务直调；启动全量校验保证配置引用未注册动作拒绝启动 | ✅ 可承载 |
| X3 三层战斗 | 战斗阶段动作（orbital_bombard / air_drop） | 注意：属战斗系统阶段动作（combat.phase_define actions），与规则动作注册表机制同构，题材层注册战斗阶段动作 handler | ✅ 可承载（机制同构，落点待 E16/E14 明确） |

## 六、结论

### 6.1 配置化承诺：成立，但须从"100%"修正为"~71%（严格）/ ~83%（宽松）"

- **成立范围**：17 个特征（主导归属）可由现有 18 配置扩展点 + 内置 7 动作 + 注册表 + 公式引擎 12 能力直接表达——蚁群分工、虫族进化、蛰伏、巢穴建设（组合）、菌圃共生、基础 PvE、州郡争夺、兵种克制、外交合纵、基础攻城、赛季争霸、名城争夺、舰队编队、资源星球、星际外交、定点跃迁、银河战争。
- **修正原因**：05 验证为文档映射级（扩展点名存在=覆盖），本表为契约表达力级（字段/语义/行为/机制均承载=覆盖）。差额 7 个特征（29.2%）对应"扩展点字段缺口 / 动作缺口 / 机制骨头缺口"三类。
- **对 E4 报告的回写**：高风险#1（公式表达力）与高风险#2（注册表扩展）的 P1 落地，正是把上述 7 个差额中"公式/动作"类缺口从"缺"降为"可扩展"的关键——**公式引擎已覆盖全部公式需求，注册表已覆盖全部动作需求**，剩余缺口收敛为"数据/语义扩展点（2 个）+ 机制骨头（3 个）"。

### 6.2 必须走扩展开发的特征（C 类，与终版一致）

| 特征 | 扩展内容 | 归属 |
|------|---------|------|
| K2 信息素路径 | 新扩展点（信息素场）+ 新动作 handler（release_pheromone） | extensions/insect |
| S2 武将策反 | 新动作 handler（change_owner） | extensions/sangoku |
| X3 三层战斗 | 题材层战斗阶段动作（层内演算） | extensions/starcraft |
| X7 跃迁变体 | 新扩展点（随机目的地生成器）+ 题材层移动动作 | extensions/starcraft |

> 与终版 C 类原文一一对应：昆虫信息素路径 / 三国计策 / 星际三层战斗、星际跃迁。**全部可由注册表/扩展点机制承载，无需修改框架核心代码**——这正是 ADR-002/003"框架零改动扩展"要兑现的场景。

### 6.3 必须等框架骨头建成的特征（A 类，计划内，非题材负担）

S4 内政建设（建筑升级 #14）、S7 科技树（个人科技 #18）、X5 科技跃迁（个人科技 #18）——机制缺失属 P3 六骨头计划内，配置契约（buildings/techs Schema）已就绪，骨头建成即配置化。

### 6.4 行动建议（对接 E16 题材扩展验收）

1. **E16 验收基线**：题材层至少落地 `release_pheromone`（信息素路径）与 `change_owner`（策反）两个注册表动作，验证"框架零 diff"承诺（对齐 ADR-002 验收与 E4 报告第五章遗留）；
2. **新扩展点立项**：信息素场（movement_path_markers）、随机目的地生成器（movement_teleport_destination_generators）、真 3D 距离（map_distance_formula，可选）三个扩展点契约待 E14/E16 期补充；
3. **文档口径修订**：05-通用性验证 README 的"玩法特征覆盖率 24/24 = 100%"应加注"文档映射级结论，契约表达力级核查见本表（~71% 严格口径）"；
4. **E7 契约冻结**：本表作为契约冻结草案的"表达力附件"，随 E7 proto 契约同步评审。
