## 二、三高风险结论（核心章节）

### 2.1 高风险#1 公式表达力 —— ✅ PASS

**评审原文**：四则运算+变量替换的公式引擎撑不起真实 SLG 公式；若失败则终止"配置化承诺"，改走扩展点方案。

**验证结论：表达力验证通过，AST 方案实际效果成立，"配置化承诺"在自动演算型战斗范围内可继续。**

**证据 1：8 条真实昆虫公式全部可编译、可求值、结果与手工计算一致**（`formula_test.go` `TestVerificationSet`，种子固定 `20260811`）

| # | 公式 | 形态 | 求值结果 |
|---|------|------|---------|
| 1 | 伤害=攻击×(1−防御/100)×克制系数×random(0.9,1.1) | 算术+随机 | 区间 [108,132) 且确定性成立 |
| 2 | 血量=基础×(1+等级×0.1)×(1+种族防御修正) | 嵌套算术 | 156 精确 |
| 3 | 攻击=基础×(1+等级×0.1)×(1+种族攻击修正) | 嵌套算术 | 71.5 精确 |
| 4 | 升级成本=基础成本×(1+等级×0.5) | 算术 | 3000 精确 |
| 5 | 战斗力=Σ(血量×攻击×克制系数)/100 | 算术 | 75 精确 |
| 6 | 首击伤害=if(种族==螳螂, 伤害×2.0, 伤害) | **条件分支** | 240（螳螂）/120（非螳螂） |
| 7 | 保留量=min(原值×keep_ratio, keep_amount) | 函数+比较 | 300 精确 |
| 8 | 基础伤害=max(atk×counter−def×terrain_mod, 1) | 函数钳制 | 54 精确 |

- 8 条覆盖了评审指出的全部缺口形态：**条件分支（#6）、随机（#1）、函数调用（#7/#8）、嵌套（#2/#3）**；
- 额外验证：运算符优先级、一元负号、比较/逻辑（`and/or/not`）、函数嵌套、`if` 惰性求值（未选分支不求值，避免除零）——均通过（`TestArithmetic`/`TestComparisonAndLogic`/`TestBuiltinFunctions`/`TestIfConditional`）。

**证据 2：govaluate/Lua 否决后的 AST 方案实际效果**（ADR-001 决策 D）

| 维度 | 实际效果 |
|------|---------|
| 语法能力 | lexer+递归下降 parser（212+273 行），覆盖 EBNF 全规格：优先级/一元/比较/逻辑/函数/括号/嵌套深度 ≤10 |
| 函数库 | functions.go 210 行：min/max/floor/ceil/round/random/clamp/abs/if 全部落地，`random` 三签名 |
| 执行模型 | 直接 AST 树遍历（eval.go 145 行），未做字节码 VM——与 ADR-001 3.4"避免过早优化"决策一致 |
| 零依赖 | 无第三方表达式库，无 Lua VM；`go.mod` 仅 testify/zap 等基础设施依赖 |
| 编译期校验 | 非法公式（未定义函数/语法错误/超深度）返回文件+公式ID+原因+修复建议，拒绝加载（formula_test.go 错误用例覆盖） |

**证据 3：随机确定性验证（同种子同结果）**

- `TestRandomDeterminism`：同公式+同变量+同种子两次求值**完全一致**（`assert.Equal`），不同种子结果不同；
- `TestPcg32FrozenSequence`：**冻结算法回归值**——seed=0/1 断言固定 Float64/Int63 输出序列，任何算法改动（即使行为等价）都会暴露，跨 Go 版本回放一致性由此保证；
- 战斗级种子派生 `DeriveRoundSeed(combatID, configVersion, round)`（FNV-1a，seed.go）与重放链路（replay.go）在 2.2 验证。

**结论**：验证集 8 条 + 边界用例全部通过 → **ADR-001 验收标准 1/2/3/4/6 达成**；未发现无法表达的必选公式 → 未触发"降级评审"知识缺口闭环。能力边界写回：**表达力在"自动演算型战斗 + 配置化规则"范式内成立**（评审 P4 的实时/战棋/舰队战仍列为扩展点替换场景，不改承诺）。

### 2.2 高风险#2 热更×快照×权威方 —— ⚠️ 部分通过（核心防御闭环 PASS，2 项代码级缺口 CONCERNS）

**评审原文**：热更删除兵种后 Social 按新配置回写、Combat 按旧公式计算 → 隐性引用断裂；运行中战斗引用已删除配置项；回滚未定义进行中业务版本归属。修复建议三条：①快照绑 config_version + 结算校验熔断；②回滚双向语义；③热更删除配置项扫描进行中实例。

**验证结论：修复建议①全部落地并通过测试；②③仅部分落地（引用计数保留已实现，回滚命令/实例扫描器为代码缺口）。核心防御闭环（快照冻结→版本化查询→结算熔断→重放一致）经真实代码验证成立。**

**证据 1：config_version 绑定 + GetWithVersion 版本化查询（ADR-004 3.1）✅**

- `snapshot.go`：`CombatSnapshot.ConfigVersion`（开战冻结）、`CombatType`/`FormulaID`/`LootRuleID`/`SkillIDs`/`PropEntry.UnitType` 全部以快照版本为基准；
- `query_api.go`：`ConfigQueryAPI` 扩展 `GetWithVersion/HasWithVersion/PinVersion/UnpinVersion` 四个方法；
- `versioned_store.go`：版本化存储实现——`versions map[版本]map[扩展点]map[key]value` + `refs` 引用计数；`Pin/Unpin` 保证**进行中实例引用的版本永不因历史滚动清理**（`PruneUnreferenced` 只清理计数为 0 且超出 `maxConfigVersionHistory=10` 的版本）；
- 测试：`versioned_store_test.go` 6 个 Test 覆盖 Put/Get/Has/Pin/Unpin/Prune 全路径。

**证据 2：结算校验 + 熔断协议（ADR-004 3.2）✅**

- `circuit_break.go`：`ValidateSnapshotConfig` 校验战斗类型/伤害公式/参战双方兵种/战利品规则在快照版本存在；`ResolveCircuitBreak` 按策略决策——默认 `ForceDraw`（强制平局、不发战利品、不发赛季积分），`FallbackSettle` 仅当兜底公式在快照版本存在（否则回落平局）；
- `settle.go`：结算编排完整接入——`ValidateSnapshotConfig` → 有缺失走 `ResolveCircuitBreak` → 发布 `combat.circuit_broken` 事件；
- **经济安全性优先于战斗结果完整性**的决策依据（ADR-004 3.2）在代码注释与默认策略中固化；
- 测试：`circuit_break_test.go` 覆盖兵种删除→熔断、兜底公式缺失→回落平局等路径（combat 包 42 Test 全绿）。

**证据 3：重放一致性（ADR-004 3.5 / ADR-001 验收"战斗回放逐轮一致"）✅**

- `replay.go`：战报记录 combatID+configVersion+种子+逐轮结果；`ReplayCombat` 按战报 config_version 取公式源码编译、`DeriveRoundSeed` 重建 Pcg32 重算伤害、逐轮比对；
- 不一致根因四分类：公式缺失/随机漂移/属性快照变化/数值偏差——**覆盖 ADR-004 场景 A/B/C 的重放侧检测**；
- 测试：replay 10 Test 全绿，91.5% 覆盖率。

**缺口#1：热更删除实例扫描（ADR-004 3.3）——代码未实现 ❌**

- `ConfigDependencyScanner` / `ScanCombatRefs` / `PrecheckDeleteRefs` 在 ADR-004 3.3 定义，`grep server/` **零命中**，无实现文件；
- 影响：评审修复建议③"热更删除配置项时扫描进行中实例引用（阻塞/降级）"未落地——当前仅靠结算熔断兜底（删除后结算才发现缺失），**风险前置能力缺失**；
- 处理：转 P3（E8-E13 六骨头落地后有真实实例可扫）+ E6 存量补齐，不阻塞 M1（熔断兜底已保证不 panic、不误发战利品）。

**缺口#2：双向回滚命令（ADR-004 3.4）——仅落地引用计数 ❌**

- `Pin/Unpin` 引用计数保留已实现（版本不因回滚清理），但**回滚操作本体**（RollbackConfig 命令、审计日志、进行中实例归属切换）无代码；
- 处理：转 E6（存量基础补齐），与热更链路一起落地。

**结论**：评审修复建议①（快照绑定+结算熔断）**完整落地且测试绿**，②③的**配套机制**（引用计数版本保留）落地但**命令/扫描器本体缺失**。热更场景 A（删除兵种→结算熔断不 panic、不误发）经 `circuit_break_test.go` 验证成立；场景 B/C（回滚/中途热更的重放一致性）经 replay 链路验证成立。→ **高风险#2 判定：部分通过（核心闭环 PASS，前置扫描与回滚命令 CONCERNS）**。

### 2.3 高风险#3 工程节奏 —— ✅ PASS

**评审原文**：P0 六组纯重构共享同一失败面；"先重构后功能"空转风险；8 微服务基础设施过重。修复建议：先做垂直切片（单 module 或最小 3 服务），验证三高风险后再决定模块拆分。

**验证结论："先切片后重构"实际成立，垂直切片验证了评审建议 1，未发生重构空转。**

**证据 1：顺序约束实际成立（原计划 vs 实际情况）**

| 计划项 | 计划 | 实际 | 判定 |
|--------|------|------|------|
| E1 公式引擎最先启动（最大知识缺口） | 6d | AST+函数库+种子随机 1074 行实现，92.1% 覆盖 | ✅ 计划与实际一致 |
| E2 行为注册表先于 P3（避免两套扩展机制） | 3d | action_registry + 7 动作 init 注册 + 启动校验，453 行实现 | ✅ 计划与实际一致 |
| E3 切片主链路 + config_version 绑定 | 10d | 快照/熔断/重放/伤害接入，983 行实现 + integration 3 测试 | ⚠️ 战斗段完成，S6 主链路依赖 P3 |
| E4 切片验证报告 | 1d | 本报告 | ✅ |
| 4 项 ADR 全部 Accepted 且与代码一致 | — | ADR-001~004 冻结，代码逐项可追溯 | ✅ |

**证据 2：无重构空转**

- P1 直接产出**可测试功能链路**（公式引擎/注册表/快照/熔断/重放），非目录搬家/import 迁移类纯重构；
- 每 Epic 先写测试后实现（验证驱动），产出即带测试证据路径（第六章）；
- 代码保持 DDD 四层 + 共享内核端口适配（ActionAccessor 端口、FormulaEvaluator 最小接口），未因切片引入技术债。

**证据 3：基础设施收敛验证**

- P1 在**单进程多模块**（server/shared + server/combat + integration）内完成切片验证，未引入 NATS/etcd/Redis 微服务栈——对齐评审建议 1"单 module 跑通再决定拆分"与 YAGNI 收敛；
- 版本化配置存储用**内存实现**（versioned_store.go）即可满足切片验证，验证了"P1 切片不需要分布式基础设施"的判断。

**结论**：评审担心"先重构后功能使全部服务共享同一失败面"未发生——P1 先做功能切片、用最小基础设施验证三高风险，节奏正确。→ **高风险#3 判定：PASS**。

### 5.2 判定

> **M1 里程碑判定：PASS（with CONCERNS）**

- **PASS 依据**：M1 DoD 三条全部满足——三高风险均有代码级结论、随机回放一致性经重放链路验证、工作量校准完成且总体估算可信；
- **CONCERNS**：
  1. 高风险#2 的"热更删除实例扫描"与"双向回滚命令"为代码级缺口，**M1 只要求"有结论"不要求"全闭环"**，但进入 P3 前必须排期闭环（本报告建议 E6 承接）；
  2. config 包覆盖率 59.2% 未达 80% 线（E6 补测）；
  3. E3-S6 主链路后半段依赖 P3 骨头，**"昆虫可玩"（M4）之前的主链路 e2e 依赖 P3 完成度**，建议 P3 期间同步补 integration 主链路测试；
- **下一里程碑门禁**：M2（E5-E7）DoD"L1 依赖单向、启动校验、CI 门禁全绿、契约冻结草案"——其中契约冻结草案（E7）与 config 覆盖率（E6）建议作为 M2 前置复核项。
