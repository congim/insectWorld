# 技术架构 · 规则系统 

> 条件-动作规则的注册和执行引擎——"当X发生且Y条件满足时，执行Z动作"的可编程层。

---

## 核心模块定义

**是什么**：条件-动作规则的注册和执行引擎——"当X发生且Y条件满足时，执行Z动作"。规则系统是框架的"可编程层"，让策划能用配置实现复杂逻辑。

**为什么是核心模块**：每个SLG都有规则。无论是"占领3座城池后触发加成"、"赛季末联盟积分排名奖励"还是"首次击杀Boss获得称号"，底层都是条件-动作规则。规则系统让这些逻辑从硬编码变为可配置。

**配置注入方式**：

| 扩展点 | 用途 | 契约摘要 |
|-----------|------|---------|
| rule_definitions | 规则定义 | 规则ID→{触发事件, 条件表达式, 动作列表, 优先级}映射 |
| rule_groups | 规则组 | 组ID→{规则列表, 互斥策略, 执行策略}映射 |
| rule_conditions | 条件库 | 条件ID→{类型, 参数}映射，可复用的条件片段 |
| rule_actions | 动作库 | 动作ID→{类型, 参数}映射，可复用的动作片段 |
| rule_priority_policy | 优先级策略 | 策略定义，决定同优先级规则的执行顺序 |
| rule_cooldown_rules | 冷却规则 | 规则ID→{冷却时间, 冷却作用域}映射 |

## 框架默认行为

- 默认优先级策略：数值越大越先执行
- 默认互斥策略：同组规则只执行优先级最高的
- 默认执行策略：串行执行
- 默认无冷却
- 规则执行触发 `rule.executed` 事件
- 规则条件不满足触发 `rule.condition_failed` 事件

## 约束

- 规则的动作不可是"修改规则自身"（防止无限递归）
- 规则执行有超时保护（防止死循环）
- 规则组内的互斥检查在执行前完成
- 规则的条件表达式必须是无副作用的纯函数

### 边界条件

| 参数 | 默认值 | 可配 | 说明 |
|------|--------|------|------|
| max_rules_per_event | 100 | 是 | 单事件最大规则数，超限拒绝注册 |
| rule_execution_timeout_ms | 50 | 是 | 单规则执行超时，超时则终止该规则并记录ERROR |
| max_rule_groups | 50 | 是 | 规则组总数上限 |
| max_condition_eval_depth | 10 | 是 | 条件表达式最大嵌套深度 |
| rule_cooldown_precision_seconds | 1 | 是 | 冷却时间精度（最小粒度） |
| max_actions_per_rule | 20 | 是 | 单规则最大动作数 |
| rule_recursion_limit | 3 | 是 | 规则间递归触发最大深度（A触发B，B触发C…） |

## 与其他核心模块的关系

规则系统**依赖事件总线、实体系统、Buff系统**，**被多个玩法核心模块使用**：

- **依赖事件总线**：规则的触发依赖于事件（`trigger_event` 字段引用事件类型）
- **依赖实体系统**：规则的条件评估和动作执行针对实体（查询属性、标签等）
- **依赖Buff系统**：规则的动作之一是施加/移除Buff（`apply_buff` / `remove_buff`）
- **依赖经济系统**：规则的动作之一是发放资源（`grant_resource`）
- **被联盟系统使用**：联盟升级、外交变更等逻辑通过规则实现
- **被赛季系统使用**：赛季阶段切换、奖励发放、重置逻辑通过规则实现
- **被事件总线使用**：规则执行发出 `rule.executed` 事件供其他核心模块监听
- **被网络同步使用**：规则执行结果需要同步到客户端

规则系统是框架的"可编程层"，它将其他核心模块的功能（Buff、资源、实体生成）组合成可配置的复杂逻辑，是策划最常使用的扩展点。
