# 技术架构 · 持久化 

> 为游戏数据提供持久化框架级支持——存档点定义、增量持久化、数据版本迁移、回滚。

---

## 核心模块定义

**是什么**：为游戏数据提供持久化框架级支持——存档点定义、增量持久化、数据版本迁移、回滚。

**为什么是核心模块**：SLG是长线运营游戏，数据持久化是基础设施。框架提供持久化，具体存档策略和数据结构由内容配置。

**配置注入方式**：

| 扩展点 | 用途 | 契约摘要 |
|-----------|------|---------|
| persistence_entities | 持久化实体 | 实体类型→{存档策略, 存档频率, 存档字段}映射 |
| persistence_triggers | 存档触发器 | 触发器ID→{触发事件, 存档范围, 存档方式}映射 |
| migration_scripts | 迁移脚本 | 版本号→{升级逻辑, 降级逻辑}映射 |
| snapshot_rules | 快照规则 | 规则ID→{触发条件, 快照范围, 保留数量}映射 |
| rollback_rules | 回滚规则 | 规则ID→{触发条件, 回滚范围, 回滚点}映射 |
| archive_rules | 归档规则 | 规则ID→{归档条件, 归档范围, 保留期限}映射 |

## 扩展点契约

###  persistence.persistence_entities

| 字段 | 值 |
|------|---|
| extension_point_id | persistence.persistence_entities |
| core_module | 持久化 |
| purpose | 定义需要持久化的实体类型 |
| input_contract | `{ "type": "object", "schema": { "additionalProperties": { "type": "object", "properties": { "entity_type": { "type": "string" }, "save_strategy": { "type": "string", "enum": ["incremental", "full_snapshot", "event_sourcing"] }, "save_frequency_seconds": { "type": "number", "minimum": 1 }, "save_fields": { "type": "array", "items": { "type": "string" } }, "compress": { "type": "boolean" } }, "required": ["entity_type", "save_strategy", "save_frequency_seconds"] } }, "required": true }` |
| output_contract | `{ "type": "null", "description": "注册成功无返回值" }` |
| validation_rules | `[{"rule_id":"valid_entity_type","rule_type":"reference_check","parameters":{"field":"entity_type","references":"entity.entity_types"},"error_message":"实体类型必须引用已定义的实体类型"}]` |
| default_value | `{}` |
| examples | `[{"entity_type":"building","save_strategy":"incremental","save_frequency_seconds":300,"save_fields":["level","hp","owner"],"compress":true}]` |

## 框架默认行为

- 默认存档策略：增量存档
- 默认存档频率：每5分钟 + 关键事件时
- 默认无迁移脚本
- 默认快照：赛季开始和结束时
- 默认无回滚
- 默认归档：超过3个赛季的数据归档

## 约束

- 持久化操作是异步的，不阻塞游戏主循环
- 迁移脚本必须支持双向迁移（升级和降级）
- 快照数据不可修改
- 回滚操作不可撤销
- 持久化失败触发 `persistence.error` 事件

### 边界条件

| 参数 | 默认值 | 可配 | 说明 |
|------|--------|------|------|
| max_concurrent_saves | 10 | 是 | 最大并发存档操作数 |
| save_batch_size | 100 | 是 | 批量存档每批实体数 |
| save_timeout_seconds | 30 | 是 | 单次存档操作超时 |
| max_snapshot_size_mb | 100 | 是 | 单快照大小上限 |
| max_snapshots_retained | 20 | 是 | 快照保留数量上限 |
| migration_timeout_seconds | 300 | 是 | 数据迁移超时 |
| max_archive_age_seasons | 10 | 是 | 归档数据最大保留赛季数 |
| storage_backends | redis,mysql,mongodb | 是 | 存储后端类型（热数据Redis/冷数据MySQL/文档MongoDB） |

## 与其他核心模块的关系

持久化是**横切关注点**，依赖所有核心模块（需要持久化所有核心模块的状态）：

- **依赖实体系统**：持久化实体状态（引用 `entity.entity_types` 校验）
- **依赖移动系统**：持久化移动状态（当前位置、路径）
- **依赖战斗系统**：持久化战报数据
- **依赖经济系统**：持久化资源数据
- **依赖地图系统**：持久化地图变更（地形、区域）
- **依赖Buff系统**：持久化持久型Buff状态
- **依赖联盟系统**：持久化联盟数据（创建/解散触发存档）
- **依赖赛季系统**：持久化赛季数据（赛季开始/结束触发快照）
- **依赖规则系统**：持久化规则冷却状态、一次性规则执行标记
- **依赖事件总线**：监听关键事件触发存档（`combat.ended`、`season.ended` 等）
- **被网络同步依赖**：重连时从持久化恢复状态

持久化不提供任何游戏逻辑，只负责将其他核心模块的状态保存到存储介质并在需要时恢复。
