# AI 开发工作流

> 状态：已接受  
> 本文解释协作流程；强制编码规则以仓库根目录 `AGENTS.md` 为准。

## 目标

AI 的价值是缩短“理解 → 修改 → 验证”的循环，不是批量生成未经验证的代码。所有代理都应把仓库事实、任务边界和可执行证据放在输出篇幅之前。

## 标准流程

### 1. 理解

- 先读 `README.md`、`docs/README.md` 和目标目录最近的 `AGENTS.md`；
- 优先使用代码知识图谱发现符号与调用关系；不可用或结果不足时再用 `rg`；
- 检查 `git status`，区分用户已有改动和本次任务改动；
- 找到产品边界、相关 ADR、接口契约和测试，不以单份历史规格作为唯一依据。

### 2. 定界

实施前用一句话说明可观察目标，并确认：

- 属于通用内核、领域模块、游戏包还是代码扩展；
- 哪个上下文拥有数据和事务；
- 是否真的需要新接口、新服务、新依赖或新配置；
- 哪些内容明确不在本次范围。

如果需求跨越边界或改变已接受 ADR，先新增 ADR；普通实现任务不新增架构文档。

### 3. 设计最小改动

- 优先修改现有聚合、用例和扩展点；
- 接口只为跨层依赖、多个实现或测试替身而建；
- 不为单个任务引入框架、代码生成器或通用 `utils` 包；
- 配置只承载数据和受控表达式，不承载任意程序逻辑；
- 数据迁移、协议变更和事件变更必须有兼容策略。

### 4. 实现

- 小步提交逻辑，先写或同步修改测试；
- 保留用户未提交的无关改动；
- 错误、日志、注释、结构体字段和表名遵守 `AGENTS.md`；
- 领域层不引入基础设施 SDK；
- 外部写命令与事件消费者从一开始实现幂等。

### 5. 验证

按风险从窄到宽执行：

1. 修改包的单元测试；
2. 所属 Go module 的 `go test -race ./...`；
3. 契约、静态扫描和相关集成测试；
4. 受影响的工作区全量检查。

测试失败时必须区分“本次引入”“原有失败”“环境缺失”，不得只写“应该能通过”。覆盖率用于发现缺口，不允许为达百分比编写无断言或低价值测试。

### 6. 交付

最终说明必须包含：

- 已实现的用户可见结果；
- 关键设计取舍；
- 修改和删除的主要文件；
- 实际执行的验证及结果；
- 仍存在的风险或明确后续，不把建议伪装成已完成。

## AI 禁止事项

- 未读代码就按文档猜测接口；
- 把目录存在、代码能编译或测试数量当作功能完成；
- 未经授权覆盖、回退或格式化用户的无关改动；
- 为追求“通用”添加无调用方抽象；
- 把题材数值写进通用代码；
- 用内存 mock 通过来宣称持久化、并发或分布式一致性已经验证；
- 同时大规模改目录、协议、数据库和业务逻辑，导致无法定位回归；
- 在日志、示例或测试夹具中写入真实密钥和个人数据。

## 评审清单

评审按顺序回答：

1. 行为是否满足任务验收？
2. 数据所有权和事务边界是否正确？
3. 是否污染了通用层或形成反向依赖？
4. 重试、并发、失败和版本变化是否安全？
5. 测试是否验证行为而非实现细节？
6. 日志、指标和错误是否足以定位问题？
7. 文档是否只更新了真正变化的权威源？

发现问题按严重度报告，并给出文件、位置、触发条件和影响。没有问题时也要声明验证范围与未覆盖风险。
