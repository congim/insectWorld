# 实施路线图

> 状态：已接受  
> 原则：以可运行证据推进，不以文档数量、目录数量或任务勾选数衡量完成度。

## 阶段 0：基线收敛

目标：建立唯一产品边界、目标架构、代码地图和 AI 工作流。

验收：

- 文档有唯一入口和权威层级；
- 根目录不再保留重复的总设计、终版方案和过期计划；
- 历史规格明确降级为实施证据；
- 构建与现有测试不因文档整理受损。

## 阶段 1：最小游戏包

状态：已实现基础契约。`insect-world` 与 `frontier-demo` 已使用同一强类型加载、引用校验和版本兼容规则通过 CI；运行时领域装配归入阶段 2。

目标：创建 `gamepacks/insect-world` 的最小 manifest、schema、配置和测试，只覆盖一族、一种资源、一种单位、一种建筑和一张小地图。

验收：

- 配置可离线校验和编译；
- 稳定 ID、引用关系、版本兼容性校验完整；
- 引擎代码中没有昆虫题材词汇；
- 错误配置给出可定位到文件和字段的中文错误。

## 阶段 2：单进程垂直切片

状态：进行中。已在`server/game`跑通“加载游戏包 → 创建玩家并发初始资源 → 建造并完成建筑 → 训练并入账单位”的Growth子链路；并发重复建造只扣款一次。行军、采集、战斗、持久化与重连恢复尚未接入。

目标：在模块化单体内跑通首个闭环，避免先处理分布式复杂度。

主链路：

```text
注册/登录 → 创建玩家 → 升级建筑 → 训练单位 → 行军/采集
         → 战斗 → 资源与伤兵结算 → 保存 → 重启/重连恢复
```

验收：

- 一条自动化测试覆盖完整链路；
- 相同种子与配置版本的战斗回放完全一致；
- 重复命令和重复事件不造成重复扣款或发奖；
- 任一步骤失败时，状态可解释且可恢复；
- 日志可用同一 trace ID 串联。

## 阶段 3：边界验证

目标：验证“配置、扩展、领域模块”的边界是否真实可用。

验收：

- 增加第二个最小示例包，不修改通用内核；
- 实现一个昆虫专属扩展，不让领域模块引用昆虫代码；
- 配置热更与进行中战斗、行军、生产的切换边界有测试；
- 根据证据修订扩展接口，冻结首个兼容版本。

## 阶段 4：生产化

目标：用容量与故障测试决定部署和基础设施，而非模板化堆栈。

验收：

- 有真实流量模型和压测报告；
- 明确 SLO、备份恢复目标和告警阈值；
- 根据测量结果决定哪些上下文独立部署；
- 发布、回滚、配置灰度和数据迁移均经过演练。

## 后置清单

联盟深度玩法、完整赛季、任务成就、排行、匹配、跨服、合服、商城、邮件、聊天和复杂运营活动默认后置。它们只有在首个闭环完成、产品优先级明确并写出验收用例后才进入实施。

## 任务模板

每个可实施任务必须写清：

- 用户或系统可观察到的目标；
- 所属层级与限界上下文；
- 明确不做的范围；
- 契约、数据与兼容性影响；
- 正常、边界、重试和失败验收用例；
- 需要更新的文档与 ADR；
- 可执行验证命令。
